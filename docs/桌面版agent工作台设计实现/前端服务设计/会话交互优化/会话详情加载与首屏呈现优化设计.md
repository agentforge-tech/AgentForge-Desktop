# 会话详情加载与首屏呈现优化设计

> 范围：桌面工作台会话详情区（右侧对话区）打开 / 重开会话的呈现链路
> 方案：区分「追赶（catch-up）」与「直播（live）」两种渲染模式，封装为 `chatCatchUp` mixin
> 状态：已落地（v1），构建通过，判定与落底行为均有脚本验证
> 核心体验要求：**打开会话、内容渲染完成后，默认直接停在最新（底部）**，用户无需手动下滑

---

## 1. 背景

### 1.1 现象

重开一个**运行时间很长、且仍在运行中**的会话时：

1. 先渲染出**顶部/中段**内容（思考过程、工具调用），而不是直接展示最新；
2. 过一会儿正文才追到最新，期间内容一个字一个字往外蹦；
3. 中途**短暂闪过**审核 / ask_user 卡片，输入框被禁用一瞬，让人误以为"当前最新就是这张待办"。

会话越长越明显。

### 1.2 关键事实：运行中会话的内容是 SSE 重拉出来的

`ai_agent_session_message.events` 列只在三个时机写入：

| 时机 | 代码位置 |
| --- | --- |
| 终态收口（成功/失败/取消） | `SessionLifecycleMiddleware` `finishState` |
| 挂起等人工处理 | `SessionLifecycleMiddleware.java:215` `markWaitingForHitl` |
| 订阅端发现已终态且 events 为空 | `ReconnectableChatStreamService.java:106` |

**正常运行中的消息（status 1/2/7）没有任何一处写 `events`**。事件只增量追加在事件表里（`BufferedMessageEventSink.java:86`），数据库该列是空的。

于是打开运行中会话时：

```
fetchSessionMessages → record.events 为空
  ↓
replayMessage 解析出 0 个事件 → parts = []、lastEventSeq = 0
  ↓
consumeTask → streamChatTask(messageId, afterSeq = 0)
  ↓
后端从 seq=1 开始，把本轮全部历史事件按批密集重推
```

**前端打开运行中会话时几乎是空白的，整段内容全靠 SSE 回放补齐。**

### 1.3 病根：回放走了直播的渲染管道

后端重推积压的节奏（`ReconnectableChatStreamService.java:74-88`）：每轮 `awaitAfter` 立刻返回满 100 条，推完立刻下一轮，**连续、稠密、无间隙**。

这套 backlog 被灌进为直播设计的管道，于是每批都做了直播才该做的事：

| 直播管道的设计 | 用在回放上的后果 |
| --- | --- |
| `handleEvent` 末尾每条事件都 `scroll()`（`ChatWorkbench.vue:1476`） | 事件成百上千条，每条滚一次 |
| 正文走逐字动画（`charDelay = 40ms`） | 几万字也一个个蹦，动画追不上推送 |
| 中断卡片见到 PENDING 就弹阻断确认（`ChatWorkbench.vue:651`） | 回放到历史中断事件时弹出早已失效的卡片 |
| 过程区按 `running` 展开 | 早期 think / tool_call 先渲染 → 就是"顶部的 message 阶段" |

**不是渲染量太大，是渲染语义用错了。**

---

## 2. 核心结论：追赶 ≠ 直播

同一个 SSE 连接有两个阶段，必须区别对待：

| | 追赶（catch-up） | 直播（live） |
| --- | --- | --- |
| 何时 | 从 `afterSeq` 补齐积压时 | 追平之后 |
| 事件密度 | 极高，连续无间隙 | 稀疏，数百 ms 到数秒 |
| 正文动画 | **关闭**，直接终态渲染 | 保留逐字 |
| 滚动 | **不滚**，追平后一次性落底 | 每条事件跟随 |
| 锚点同步 | 追平后同步一次 | 200ms 节流 |
| 中断卡片 | **不弹**阻断确认 | 正常弹 |

**切换点 = 静默窗口**：收不到新事件超过阈值，即认为追平。

方案的重要特性是**误判方向不对称**：

| 误判方向 | 后果 |
| --- | --- |
| 追赶误判成直播 | 退回现状（有动画、逐条滚动），不崩 |
| 直播误判成追赶 | 动画被关掉，字直接出现，不算错 |

因为"追赶态"本质是**更保守的渲染**，判早了只是少播点动画，所以不会比现在更差。

---

## 3. 判定：事件到达密度

### 3.1 为什么不能只看静默

只用"静默多久"会误判：网络抖动或主线程被 markdown 解析阻塞时，SSE 帧在缓冲区排队，前端"看起来"静默几百 ms，此时积压还没推完，提前切 live 就开始播动画。

所以要判断**"这次静默之前是不是在密集推送"**：

```
进入追赶：连续 CATCHUP_BURST_MIN 条事件，相邻间隔都 ≤ CATCHUP_BURST_GAP_MS
退出追赶：进入后，静默超过 CATCHUP_GAP_MS
```

关键：**必须"曾经密集过"才允许进入追赶**。稀疏直播（间隔几秒一条）的 `burst` 永远是 1，达不成阈值，因此**本来就是直播的会话永远不会被误判**。

### 3.2 阈值

| 常量 | 值 | 依据 |
| --- | --- | --- |
| `CATCHUP_BURST_GAP_MS` | 120ms | 积压推送帧间隔远小于此；直播 delta 间隔远大于此 |
| `CATCHUP_BURST_MIN` | 3 | 连续 3 条才确认突发，单条抖动不误判 |
| `CATCHUP_GAP_MS` | 400ms | 必须大于后端 `POLL_MS`(200ms)，给网络与主线程抖动留余量 |
| `SETTLE_MAX_MS` | 320ms | 落底收敛的最长观察窗口 |

### 3.3 状态机

```
  普通事件流（burst 不达标）
  ┌────────────────────────────┐
  ▼                            │
[live] ──连续 3 条 ≤120ms──▶ [catching]
                                │
                     静默 > 400ms│
                                ▼
                          [live] + 落底收敛
```

每条 answer 独立一份状态。实现上不做"只判定末条"的特例，因为按 answer 各自持有状态更简单，也不会误伤。

## 4. 实现：`chatCatchUp` mixin

### 4.1 为什么封装

页面已挂载 `mixins: [chatAutoScroll, chatAnchorNav]`（`ChatWorkbench.vue:506`）。追赶判定与它们强相关（要抑制滚动、协同锚点同步），直接写进 `ChatWorkbench.vue`（已 1869 行）会和这两个 mixin 的职责搅在一起。

因此抽成 `src/utils/chatCatchUp.js`，遵循现有 mixin 范式，**未接入时行为与现状完全一致**。

### 4.2 对外 API

| 名称 | 类型 | 用途 |
| --- | --- | --- |
| `catchUpActive` | data | 会话级追赶总开关，中断卡片门禁读它 |
| `noteCatchUpEvent(answer)` | method | 每个 SSE 事件调一次，做密度判定 |
| `beginCatchUp(answer)` | method | 重连且 events 为空时**前置**进入追赶，消除首帧闪烁 |
| `isCatchUp(answer)` | method | 该消息是否应抑制滚动 / 锚点同步 |
| `settleBottom({ force })` | method | 落底收敛；`force` 用于刚打开会话 |
| `teardownCatchUp()` | method | 切会话 / 销毁时复位 |
| `isCatchingUp(message)` | 导出函数 | 纯函数：是否处于追赶态 |
| `shouldStreamContent(message)` | 导出函数 | 纯函数：正文是否走逐字动画 |

`shouldStreamContent` 特意抽出：优雅模式与调试模式原本各写了一份 `contentStreaming` 判断，结构相同、容易漂移，收敛到一处后**两种模式行为永远一致**。

`beginCatchUp` 补的是密度判定的盲区：密度判定要等连续 3 条事件才生效，在那之前首帧已按 `running` 渲染。而重连时若 `lastEventSeq === 0`，说明 `events` 为空、整段内容都要靠 SSE 回放，**必然是追赶**，可直接前置判定。

### 4.2.1 追赶期**只**抑制哪些行为（重要边界）

初版曾把"过程区是否展开、标题是否显示正在处理"也纳入追赶期抑制，导致两个真实缺陷：

| 缺陷 | 现象 | 成因 |
| --- | --- | --- |
| 运行中却显示"已完成" | 过程区标题突然变成「已完成」 | `statusTitle` 前两个分支都依赖实时态，追赶时全不命中，落到兜底 `'已完成'` |
| 收拢后又重新展开 | 过程区先收起来，过一会儿又弹开 | `processOpen` 绑了 `catchingUp`，追平瞬间由 `false → true` 反转 |

**结论：追赶期只抑制「动画 / 逐条滚动 / 中断卡片」这三类副作用。**
过程区展开状态、状态标题、"正在思考"指示一律按 `status` 正常判定——它们本来就该是实时态，压制它们既无收益，又会造成上述跳变。

对应地，`isLiveMessage` 已删除，渲染层只保留 `shouldStreamContent` 一处改动。

### 4.3 实现要点

**① 状态挂 WeakMap，不进 Vue data**

```js
this._cuStates = new WeakMap()   // answer → { lastAt, burst, catching, timer }
```

事件高频，判定状态若进响应式 data，每个事件都会触发依赖收集与重渲染。WeakMap 随消息对象生命周期回收，无需手动清理。只有驱动渲染的 `message.catchingUp` 走响应式，用 `$set` 兜底。

**② 落底收敛：按"高度稳定"判完成，而不是等固定时间**

只设一次 `scrollTop = scrollHeight` 不够，首帧之后高度还会变（缩略导航让位 padding 触发 `chat.css:728` 的重排、Markdown 高亮与图片回流）。

最初实现用「双 rAF + 320ms 窗口」，实测出现**打开后差一截、要用户自己往下滑**，原因有二，都已修正：

| 缺陷 | 成因 | 修正 |
| --- | --- | --- |
| 收敛被提前打断 | 320ms 对长会话首次渲染太短，超时即收手，此时还在变高 | 改为**高度连续 3 次采样不变**才判定收敛；320ms 上限放宽到 1500ms 仅作极端兜底 |
| 被跟随状态挡住 | 原 `pin()` 里 `if (isUserScrolledUp) return`，程序化滚动把它置真后就永久停手 | 打开会话走 `force` 模式：完全忽略该标志；只有真实输入（`wheel` / `touchstart`）才中断 |
| 程序化滚动被误判成"用户上滑" | `onFeedScroll` 按 `distance > 80` 判定，内容刚挂载时 `scrollHeight` 还在涨，会被置 `followScroll = false` | 收敛期置 `_cuSettleActive`，在 `onFeedScroll` 开头短路（沿用既有 `navigatorJumping` 的同一手法） |

`force` 模式还先**同步**落一次底（不等 rAF），避免双 rAF 期间出现"停在顶部"的一帧。

追平场景（非 `force`）保留 `isUserScrolledUp` 保护：用户已上滑时不强拉。

### 6.1 `src/utils/chatCatchUp.js`（新增，约 300 行）

模块头部声明与阈值常量：

```js
/** 静默多久认为追平。需大于后端 POLL_MS(200ms)，留出网络与主线程抖动余量。 */
const CATCHUP_GAP_MS = 400

/** 相邻事件间隔小于该值视为"同一批突发"。 */
const CATCHUP_BURST_GAP_MS = 120

/** 连续突发达到该条数才认为"确实在追赶"，普通直播事件稀疏、达不到。 */
const CATCHUP_BURST_MIN = 3

/**
 * 落底收敛的硬上限。
 * 必须留足余量：长会话首次渲染（Markdown 高亮、轨道让位重排）远超 320ms，
 * 上限过小会把收敛强行打断，表现就是"差一截，要自己往下滑"。
 * 正常情况由"高度连续稳定"判据提前收手，这里只是极端兜底。
 */
const SETTLE_MAX_MS = 1500

const now = () =>
  typeof performance !== 'undefined' && typeof performance.now === 'function'
    ? performance.now()
    : Date.now()
```

三个导出纯函数，两种渲染模式共用：

```js
/** 该消息当前是否处于追赶态。 */
export function isCatchingUp(message) {
  return Boolean(message && message.catchingUp)
}

/** 正文是否走流式（逐字）渲染。追赶期一律不走。 */
export function shouldStreamContent(message) {
  if (!message || isCatchingUp(message)) return false
  if (message.content) return false
  if (message.status !== 'running') return false
  const parts = message.parts || []
  for (let index = parts.length - 1; index >= 0; index -= 1) {
    const part = parts[index]
    if (part.type === 'response_segment' && part.status === 'streaming') return true
  }
  return false
}

```

密度判定与模式切换：

```js
/** 每个 SSE 事件调一次。只做算术与一次 setTimeout 重置，不涉及 DOM 与遍历。 */
noteCatchUpEvent(answer) {
  const state = this.catchUpState(answer)
  if (!state) return
  this.ensureCatchUpFlag(answer)

  const at = now()
  const gap = state.lastAt ? at - state.lastAt : Number.POSITIVE_INFINITY
  state.lastAt = at
  state.burst = gap <= CATCHUP_BURST_GAP_MS ? state.burst + 1 : 1

  // 首次达到突发阈值才进入追赶态：稀疏直播永远不会命中。
  if (!state.catching && state.burst >= CATCHUP_BURST_MIN) {
    this.enterCatchUp(answer, state)
  }
  this.armCatchUpIdle(answer, state)
},

/**
 * 显式进入追赶：用于"重连且 events 列为空"这种**确定性**场景。
 * 密度判定要等连续 3 条事件才生效，在那之前首帧已按 running 渲染（会闪）。
 * 而 lastEventSeq === 0 说明整段内容都要靠 SSE 回放，必然是追赶。
 */
beginCatchUp(answer) {
  const state = this.catchUpState(answer)
  if (!state) return
  this.ensureCatchUpFlag(answer)
  this.enterCatchUp(answer, state)
  this.armCatchUpIdle(answer, state)
},

/** 静默窗口重新计时；到期即视为追平。追赶期每个事件都会重置，不会提前结束。 */
armCatchUpIdle(answer, state) {
  if (!state || !state.catching) return
  if (state.timer) clearTimeout(state.timer)
  state.timer = setTimeout(() => {
    state.timer = null
    this.endCatchUp(answer, state)
  }, CATCHUP_GAP_MS)
},

/** 追平：撤抑制信号，并做一次落底收敛。 */
endCatchUp(answer, state) {
  const target = state || this.catchUpState(answer)
  if (target) {
    if (target.timer) clearTimeout(target.timer)
    target.timer = null
    target.catching = false
  }
  if (answer) {
    if (typeof answer === 'object') answer.catchingUp = false
    this._cuCatching.delete(answer)
  }
  this.catchUpActive = this._cuCatching.size > 0
  this.settleBottom()
}
```

落底收敛（`force` 模式 + 高度稳定判据）：

```js
settleBottom(options) {
  const force = Boolean(options && options.force)
  const feed = this.$refs && this.$refs.feed
  if (!feed) return
  this.teardownSettle()

  // force 模式下用户一有真实滚动意图就立刻让位。
  const onUserIntent = () => { this.teardownSettle() }
  if (force) {
    this._cuSettleIntent = onUserIntent
    feed.addEventListener('wheel', onUserIntent, { passive: true })
    feed.addEventListener('touchstart', onUserIntent, { passive: true })
  }

  const pin = () => {
    // 非 force（追平）时尊重跟随状态；force（打开会话）时必须到底。
    if (!force && this.isUserScrolledUp) return
    feed.scrollTop = feed.scrollHeight
  }

  feed.classList.add('is-settling')
  // force 先同步落一次：双 rAF 要等下一帧，渲染繁忙时会露出一帧"没到底"。
  if (force) pin()

  this._cuSettleRaf = requestAnimationFrame(() => {
    this._cuSettleRaf = requestAnimationFrame(() => {
      this._cuSettleRaf = null
      pin()
    })
  })

  // 高度稳定判据：连续 3 次采样高度不变，才认为真正到底。
  let lastHeight = -1
  let stableRounds = 0
  const sample = () => {
    pin()
    const height = feed.scrollHeight
    if (height === lastHeight) stableRounds += 1
    else { stableRounds = 0; lastHeight = height }
    if (stableRounds >= 3) { this.teardownSettle(); return true }
    return false
  }

  if (typeof ResizeObserver !== 'undefined' && feed.firstElementChild) {
    this._cuSettleObserver = new ResizeObserver(() => {
      if (sample()) return
      this.armSettleTicker(sample)
    })
    this._cuSettleObserver.observe(feed.firstElementChild)
  }
  this._cuSettleTicker = setInterval(() => { sample() }, 80)
  this._cuSettleTimer = setTimeout(() => this.teardownSettle(), SETTLE_MAX_MS)
}
```

滚动抑制（`handleEvent` 末尾，`L1491`）：

```js
// 追赶期不滚：积压事件成百上千条，逐条滚动会把视口反复拉扯；
// 追平后由 chatCatchUp 统一做一次落底收敛。
if (!this.isCatchUp(answer)) this.scroll()
this.scheduleAnchorSync()
```

中断卡片门禁（`activeInterrupt`，`L656`）：

```js
activeInterrupt() {
  // 追赶期一律不弹阻断式确认：回放会把历史上的 interrupt_requested 重推一遍，
  // 此时 PENDING 并不代表"现在需要你处理"，弹出会让用户误判当前待办。
  if (this.catchUpActive) return null
  // ...原查找逻辑
}
```

重连前置判定（`openSession`）：

```js
if (live && lastAssistant && lastAssistant.messageId) {
  this.running = true
  // events 列为空 → lastEventSeq 为 0 → 整段内容都要靠 SSE 回放，
  // 这是确定性的"追赶"场景，前置判定可避免首帧按 running 渲染后闪一下。
  if (!(lastAssistant.lastEventSeq > 0)) this.beginCatchUp(lastAssistant)
  // ...
}
```

布局顺序与强制落底（`openSession` 尾部，`L897`）：

```js
this.resetScrollFollow()
// 顺序关键：先测量 → 轨道就位 → 再落底。
// 原实现先 scroll 后 measure，会让位 padding 触发的重排把视口留在中途。
this.measureNavigatorSize()
this.commitAnchors({ rebuild: true })
await this.$nextTick()
if (version !== this.sessionLoadVersion) return
// force：刚打开会话必然要落到最新，不能被残留的 isUserScrolledUp 挡住；
// 只有用户真实滚动（wheel / touch）才中断收敛。
this.settleBottom({ force: true })
```

### 6.3 两种渲染模式（都要支持）

两种模式**只改一处**：`contentStreaming` 改用统一判据。过程区展开、状态标题、"正在思考"全部保持原样。

**优雅模式 `ElegantMessage.vue`**：

```js
import { shouldStreamContent } from '../../utils/chatCatchUp'

computed: {
  contentStreaming() {
    // 收敛到 shouldStreamContent：追赶期必须关掉逐字动画，
    // 否则几万字积压会一个字一个字往外蹦，远追不上 SSE 推送速度。
    return shouldStreamContent(this.message)
  }
}
```

**调试模式 `DebugMessage.vue`**：

```js
import { shouldStreamContent } from '../../utils/chatCatchUp'

computed: {
  contentStreaming() {
    // 与 ElegantMessage 共用同一判据，避免两个模式逐步漂移。
    return shouldStreamContent(this.message)
  }
}
```

二者的 `data()` / `watch` 完全不动，仍是：

```js
// ElegantMessage
data() { return { open: this.message.status === 'running' || this.message.status === 'waiting' } }
watch: { 'message.status'(val) { this.open = val === 'running' || val === 'waiting' } }

// DebugMessage
data() { return { processOpen: this.message.status === 'running' || this.message.status === 'waiting' } }
watch: { 'message.status'(val) { this.processOpen = val === 'running' || val === 'waiting' } }
```

因此"运行中"的外观在追赶期与直播期完全一致，不存在收拢/展开跳变，也不会出现「已完成」误显示。

## 9. 同期修复的两个呈现缺陷

这两个问题在落地过程中被发现，与追赶机制同属"回放/流式呈现"范畴，一并修复。

### 9.1 自然完成后不显示耗时（切换会话回来又有）

**现象**：任务自然跑完，状态栏显示"已完成"但右侧没有耗时；重新切换会话回放后又出现了。

**根因是时间类型不一致**：

| 来源 | `startedAt` 类型 |
| --- | --- |
| 后端 `SessionMessageVo.startedAt` | `'yyyy-MM-dd HH:mm:ss'` **字符串** |
| 前端新建消息 `createAnswer()` | `Date.now()` **数值** |

`replayMessage`（`sessionReplay.js:129`）把后端字符串直接赋给 `message.startedAt`，而 `finishParts`（`ChatWorkbench.vue:1593`）做的是：

```js
if (!answer.elapsedMs) answer.elapsedMs = answer.finishedAt - (answer.startedAt || answer.finishedAt)
```

`Date.now() - '2026-11-26 22:56:03'` 得到 `NaN`，`formatElapsedDuration` 对 `NaN` 返回空串，于是耗时消失。切换会话后走 `record.elapsedMs`（后端已落库的真实值），所以又有了。

**修复两处**：

1. 新增 `toEpochMs(value)`（`utils/formatDuration.js`），把字符串/数值统一转毫秒，`replayMessage` 中使用：

```js
startedAt: toEpochMs(record.startedAt),
finishedAt: toEpochMs(record.finishedAt) || null,
```

2. 补兜底收尾 `settleAnswer(answer)`：后端流自然结束时可能不下发 `resp_end`，此时 `finishParts` 从未执行、`elapsedMs` 一直为 `null`。在 `send()` 与 `submitInterrupt()` 的 `finally` 里补：

```js
/** 兜底收尾：把仍在"运行中"的 answer 归到终态并补齐耗时。 */
settleAnswer(answer) {
  if (!answer || answer.status !== 'running') return
  promoteLastResponseSegment(answer)
  answer.status = 'success'
  this.finishParts(answer)
},
```

### 9.2 过程区每轮模型文本没有 markdown 渲染

**现象**：对话 loop 过程中，每一轮模型单独发言的文本直接露出 `**加粗**`、反引号、列表符号等原始标记。

**根因**：`ResponseSegmentBlock.vue` 直接把文本塞进 `white-space: pre-wrap` 容器，完全绕过了 markdown 渲染：

```vue
<!-- 修复前 -->
<div class="response-segment" :class="mode">{{ displayContent }}</div>
```

**修复**：改为复用 `MarkdownView`，与最终回答保持一致的渲染结果：

```vue
<template>
  <div class="response-segment" :class="mode">
    <MarkdownView
      v-if="hasContent"
      :content="displayContent"
      mode="instant"
      :streaming="false"
    />
  </div>
</template>
```

两个关键选择：

| 选择 | 原因 |
| --- | --- |
| `mode="instant"` | 过程区文本是轮次中间产物，不需要逐字动画 |
| 不传 `streaming` | 避免与 `chatCatchUp` 的追赶期抑制互相干扰 |

视觉上通过 `::v-deep` 把过程区的标题字号与段间距收紧一档，保持"次级信息"层级，不与最终回答抢重点。该组件同时被优雅模式与调试模式使用，一处改动两边生效。

**验证**：`toEpochMs` 覆盖字符串/数值/空值/非法串四种输入；耗时格式化对 `1分5秒`、`1分30秒` 输出正确；构建通过。
