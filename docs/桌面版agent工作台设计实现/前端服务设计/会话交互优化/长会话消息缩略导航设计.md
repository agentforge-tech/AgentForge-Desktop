## 1. 背景与目标

### 1.1 问题

AgentForge Desktop 的单轮任务往往很长：一轮里的思考、工具调用、文件读写、追加指令会形成几十屏内容。当前会话详情区只有两种定位手段：

- 原生滚动条：Electron（Chromium）细滚动条宽度约 8px，无法承载"这一轮在说什么"的信息，长会话中拖动时也难以判断落点。
- 右下角「回到底部」按钮：只能从"停在中间"回到最新，无法向前定位。

实际用户行为是「往回翻找某一轮提问 / 某次工具结果」，而不是线性滚动。缺少结构化定位，长会话的检索成本随轮次线性上升。

### 1.2 目标

1. 在会话详情区一侧提供**轮次粒度的定位轨**：一眼看到整段会话有多少轮、当前在哪一轮。
2. 悬浮即可看到该轮的**标题与摘要预览**，不需要先跳过去再判断。
3. 点击/键盘可**平滑跳转**到该轮起点，落点精度为一轮（不是一屏）。
4. 不改变现有消息渲染、流式输出与自动跟随逻辑；纯增量能力。
5. 短会话（≤ 5 轮）不出现，避免噪声。

### 1.3 非目标（v1 不做）

| 不做 | 原因 |
| --- | --- |
| 全文搜索并高亮命中位置 | 独立能力，需后端/索引配合，放后续版本 |
| 跨会话的时间轴聚合 | 与左栏会话列表职责重叠 |
| 消息内容虚拟滚动 | 属于渲染性能专项，导航轨可在其落地后适配（见 §10） |
| 拖动过程中实时重排 | 拖动只做预览定位，松手才真正跳转 |

## 2. 参考效果拆解

Codex 的缩略定位轨可拆为 4 个可独立实现的层次：

| 层次 | 表现 | 我们的取舍 |
| --- | --- | --- |
| 刻度列 | 对话区一侧一列等距短横线，每轮一段 | 保留。等距而非按内容比例（见 §4.3） |
| 当前位置 | 视口所在一轮的刻度加宽/加深 | 保留，并扩展为"视口内覆盖段"用一条细竖条表示 |
| 悬浮预览 | 悬浮刻度弹出圆角卡片：该轮提问标题 + 助手回答摘要 | 保留，但内容改为默认只读摘要，不做内联操作 |
| 点击跳转 | 点击刻度滚动到该轮起点 | 保留，增加键盘与拖动两种等价操作 |

参考图中的刻度具有三个隐含约束，本方案全部继承：

1. 刻度**不能抢内容**：轨道落在内容内边距之外，不遮挡气泡与 Markdown 正文。
2. 刻度**命中区大于视觉区**：视觉 3px 高的线，命中区需 18–20px 宽，否则难以点中。
3. 预览卡片**不闪烁**：鼠标从刻度滑向卡片时卡片不能消失，需要"轨道 + 卡片"共享 hover 区并有进入延迟。

## 3. 现状与差距

### 3.1 现有结构

| 关注点 | 现状 | 位置 |
| --- | --- | --- |
| 消息列表 DOM | `v-for="(message, index) in messages"`，用户消息与助手消息各一行，无锚点标识 | `agentforge-desktop-ui/src/pages/workbench/ChatWorkbench.vue` L224–258 |
| 滚动容器 | `section.chat-feed.agent-debug-feed`，`@scroll.passive="onFeedScroll"` | 同上 L217 |
| 内容区宽度 | `.chat-inner` 最大 760px 居中，feed 左右内边距 32px | `agentforge-desktop-ui/src/styles/chat.css` L1431 |
| 自动跟随 | `followScroll` + `isUserScrolledUp`，距底 80px 内视为跟随 | `agentforge-desktop-ui/src/utils/chatAutoScroll.js` |
| 回到底部 | 绝对定位 `right: 26px; bottom: 118px` | `chat.css` L961 |
| 数据来源 | `messages` 由 `replaySessionMessages` 还原，助手消息含 `parts[]` | `agentforge-desktop-ui/src/utils/sessionReplay.js` |

### 3.2 差距

1. 没有"轮次"这一层概念：`messages` 是扁平的 user/assistant 交替序列，缺少可被导航消费的锚点数据。
2. 滚动状态只有布尔量（是否在底部），没有"当前第几轮"。
3. 没有滚动容器内的段落定位 API（`scrollIntoView` 会被 composer 与 header 遮挡，不能直接使用）。

## 4. 总体方案

### 4.1 一句话方案

新增一个**由 messages 派生的轮次锚点数组**，用独立的 `MessageNavigator.vue` 在会话详情区一侧渲染等距刻度轨，通过 `data-anchor-key` 把刻度与消息行 DOM 关联，点击/键盘/拖动时按锚点 offset 计算滚动位置并短暂接管自动跟随。左栏会话列表完全不动。

### 4.2 分层

```text
messages[] (已有)
    │  utils/messageAnchors.js   ← 纯函数派生，可单测
    ▼
anchors[] + activeAnchorKey + hoverAnchorKey
    │
    ├── components/MessageNavigator.vue   刻度轨 + 预览卡片 + 键盘/拖动
    │
    └── ChatWorkbench.vue   scrollToAnchor() / 视口观测 / 与 chatAutoScroll 协同
```

### 4.3 关键取舍：等距刻度 vs 比例刻度

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 按内容高度等比例 | 位置真实，可感知每轮篇幅 | 长会话中单轮被压缩到 < 8px，几乎不可点击，也无法区分相邻两轮 | 不采用为主模式 |
| 等距排列 | 每轮命中区固定，轮数即刻度数，符合"选位置"直觉 | 与真实位置有偏差 | **采用**，与 Codex 一致 |
| 混合：等距 + 悬浮真实比例指示 | 兼顾可点性与空间感知 | 实现复杂度高 | P2 可选（见 §13.2） |

等距模式下，点击刻度后滚动落点仍按**真实 offset** 计算，因此"刻度位置"和"滚动位置"不需要一致，二者只在"当前轮高亮"这一处对齐（按视口顶部命中的锚点判定）。

### 4.4 首版开关

- 轮次数 `< 6` 时整个轨道不渲染（`v-if`），不占布局。
- 提供 `localStorage` 键 `af:message-navigator` 记住"关闭"状态，便于用户隐藏（默认开启）。

### 4.5 组件拆分边界（是否单独实现）

**结论：单独实现，且不止拆成一个组件，而是拆成 4 个职责单元。** 不建议把它写成 `ChatWorkbench.vue` 内联的一段模板 + 一段样式。

#### 4.5.1 为什么不能塞进 `ChatWorkbench.vue`

`ChatWorkbench.vue` 已经 1804 行，承担会话列表、流式消费、composer、资源、权限、工作空间、技能管理等十余项职责。缩略轨虽小，但会带入 4 类高耦合能力，塞进去会直接放大现有文件的风险面：

| 带入物 | 若内联进页面的后果 |
| --- | --- |
| 指针捕获（`setPointerCapture`）、hover 延时、scrub 拖动状态 | 与 composer 的拖拽/粘贴、`@dragover` 处理共处一份 `data`，状态易串 |
| `IntersectionObserver` 生命周期 | 需在页面已有的 `loadSession` / 切会话 / `beforeDestroy` 多处插入 disconnect，漏一处就内存泄漏 |
| 刻度几何计算（`unit`/`gap`/密度）与 30+ 行样式 | 页面 `<style>` 已有大量会话列表规则，轨道样式混入后无法单独演进 |
| 预览卡片 DOM | 与消息行同层，容易踩到 `.agent-debug-*` 选择器 |

#### 4.5.2 拆分方案：4 个职责单元

```text
utils/messageAnchors.js          ① 纯函数：messages → anchors        （无 Vue、无 DOM、可单测）
utils/chatAnchorNav.js           ② 控制器 mixin：观测/跳转/节流/生命周期（无模板）
components/MessageNavigator.vue  ③ 视图：刻度轨 + 指针/键盘            （只吃 props，不查 DOM、不读 messages）
components/MessageNavigatorCard.vue ④ 展示：预览卡片                   （纯 props，单实例）
```

各单元契约：

| 单元 | 输入 | 输出 | 明确**不做**的事 |
| --- | --- | --- | --- |
| ① `messageAnchors.js` | `messages[]` | `anchors[]`、`diffAnchors()` | 不读 DOM、不访问 `this`、不发请求 |
| ② `chatAnchorNav.js` | 由 ③ 抛出的 `jump` 事件、`$refs.feed` | `navigatorActiveKey`、`navigatorJumping`、`scrollToAnchor()` | 不渲染任何节点；不改 `messages` |
| ③ `MessageNavigator.vue` | `props: anchors / activeKey` | `emit: jump(anchor)` | 不 `querySelector`、不读 `messages`、不计算滚动 |
| ④ `MessageNavigatorCard.vue` | `props: anchor / index / total` | 无（纯展示） | 不发事件、不读 store |

这样做的直接收益：

1. **可测试**：① 是纯函数，可对 `replaySessionMessages` 的真实输出直接断言，无需挂载组件。
2. **可复用**：④ 是通用"轮次摘要卡"，§13.1 的左栏会话悬浮便览可直接复用同一组件，避免两套预览样式漂移。
3. **可退化**：③ 可单独关掉（`localStorage` 开关），② 的观察器随之不启动，页面无残留逻辑。
4. **职责不越界**：页面只做三件事——传 `anchors`、接 `@jump`、加 `data-anchor-key`。

#### 4.5.3 不采用的替代方案

| 方案 | 不采用原因 |
| --- | --- |
| 内联进 `ChatWorkbench.vue` | 见 §4.5.1，状态耦合与样式污染 |
| 做成 `el-scrollbar` 的自定义滚动条 | Element UI 的 `el-scrollbar` 只支持固定宽度竖条，无法承载悬浮卡片与等距语义；且会替换掉现有原生滚动行为 |
| 用 CSS `scroll-marker` / `::scroll-marker` | Chromium 133+ 才有，Electron 31（Chromium 126）不可用；且无法做预览卡 |
| 复用现有 `InterruptCard` / `el-popover` 做卡片 | popover 走 `appendToBody`，滚动时定位跟随成本高、闪烁明显；轨道需要"单实例 + transform 跟随" |
| 一个组件包办 ①②③④ | 就是用户担心的"冗余到一个组件"，1200 行混合逻辑无法单测 |

#### 4.5.4 与页面的耦合面（仅 4 处）

1. `messages` → 传给 `buildAnchors`（页面已有此数据）。
2. 用户消息行加 `:data-anchor-key`（1 个属性）。
3. `<MessageNavigator :anchors @jump>` 插入到 shell 层。
4. `chatAutoScroll.js` 增加 `navigatorJumping` 早退与 `scrollToRatio` 兜底。

## 5. 锚点数据模型与派生

### 5.1 数据结构

```js
// 每一轮 = 一条 user 消息 + 其后到下一轮 user 之前的全部 assistant 消息
{
  key: 'u-12',            // 稳定的轮次键：'u-' + user 消息在 messages 中的下标
  userIndex: 12,
  title: '请把左侧栏改成可折叠',    // 取自 user 消息 text 首行，<= 48 字
  digest: '已修改 ChatWorkbench.vue 与 chat.css，…', // 助手首个有效文本片段，<= 96 字
  resources: 2,           // 该轮附带的本地资源数
  toolCount: 3,           // 该轮工具调用数
  status: 'ok',           // ok | running | error | cancelled | interrupt
  timeLabel: '14:21',     // 该轮 user 消息时间（数据来源见 §5.2 末尾说明）
  el: null                // 运行时填充的 DOM 引用，不参与响应式比较
}
```

`status` 判定优先级：`interrupt_card` 存在 → `interrupt`；任一 assistant `status === 'running'` → `running`；`status === 'error'` → `error`；`status === 'cancelled'` → `cancelled`；否则 `ok`。

### 5.2 派生函数

新增 `agentforge-desktop-ui/src/utils/messageAnchors.js`，纯函数、无 Vue 依赖：

```js
export function buildAnchors(messages) {
  const anchors = []
  let current = null

  const push = () => {
    if (!current) return
    anchors.push(current)
    current = null
  }

  ;(messages || []).forEach((message, index) => {
    if (message.role === 'user') {
      push()
      current = {
        key: 'u-' + index,
        userIndex: index,
        title: toTitle(message.text),
        digest: '',
        resources: (message.resources || []).length,
        toolCount: 0,
        status: 'ok',
        timeLabel: message.createTime ? formatClock(message.createTime) : ''
      }
      return
    }
    if (!current) return // 会话开头异常数据：忽略孤立助手消息
    const parts = message.parts || []
    for (const part of parts) {
      if (part.type === 'tool_card') current.toolCount += 1
      if (part.type === 'interrupt_card') current.status = 'interrupt'
    }
    if (!current.digest) current.digest = toDigest(message.content, parts)
    if (message.status === 'running') current.status = 'running'
    else if (message.status === 'error' && current.status !== 'interrupt') current.status = 'error'
    else if (message.status === 'cancelled' && current.status === 'ok') current.status = 'cancelled'
  })

  push()
  return anchors
}
```

要点：

- **只依赖 messages**，不读 DOM，可对 `replaySessionMessages` 的输出直接做单测。
- 流式过程中助手 `content` 持续增长，摘要只在 `digest` 为空时取一次，避免每帧重排（也避免预览文字不断跳动）。需要"实时跟新"时，改为取 `parts` 中最后一段的**首 96 字**，并在 §12.1 的节流窗口内更新。
- 摘要生成先走后端持久化的纯文本，**不要**对 Markdown 源码做渲染，避免悬浮卡片出现半截语法。
- **时间字段目前缺失**：`replaySessionMessages` 还原的用户消息只有 `text / rawText / resources`，`timeLabel` 需要在同一文件内把 `record.createTime`（缺失回退 `record.modifyTime`）透传到用户消息上，否则卡片元信息行只剩轮次号。

```js
// utils/sessionReplay.js —— replaySessionMessages 内，roleType === 1 分支
messages.push({
  role: 'user',
  text: record.contentText || '',
  rawText: replayUserRawText(record),
  resources: replayUserResources(record),
  createTime: record.createTime || record.modifyTime || ''
})
```

### 5.3 与 DOM 的关联

给每轮 user 消息行加锚点属性（`ChatWorkbench.vue` L225）：

```vue
<div
  v-if="message.role === 'user'"
  :key="'u-' + index"
  class="agent-debug-message-row agent-debug-message-row--user"
  :data-anchor-key="'u-' + index"
>
```

不新增包裹层、不改动 `v-for` 结构，避免影响已有 `key` 与样式选择器。

## 6. 布局与 DOM 结构

### 6.1 结构问题

`.chat-feed` 本身是滚动容器，若把轨道放进去，轨道会跟随内容滚动。因此需要一层**与滚动容器等高、不滚动**的定位容器。

推荐方案 A（新增 shell 层）：

```vue
<div class="chat-feed-shell">
  <section ref="feed" class="chat-feed agent-debug-feed" @scroll.passive="onFeedScroll">
    <!-- 既有内容，不变 -->
  </section>
  <MessageNavigator
    v-if="anchors.length >= NAV_MIN"
    :anchors="anchors"
    :active-key="navigatorActiveKey"
    @jump="scrollToAnchor"
  />
</div>
```

```css
.chat-feed-shell {
  position: relative;
  display: flex;
  flex: 1;
  min-height: 0;
}
```

`chat-feed-shell` 只承担定位上下文，`flex: 1 / min-height: 0` 保证与原布局等价（原 `.chat-feed` 的 `flex: 1` 可保留在内部）。

备选方案 B（零结构改动）：保持轨道挂在 `.conversation-stage`，用 `ResizeObserver` 读取 `.composer-wrap` 高度并写 `bottom`。缺点是 composer 高度会随草稿行数变化，需要额外同步，仅在无法改结构时使用。

### 6.2 轨道容器

**落地结论：轨道放在对话区最左侧**（与 Codex 一致），而非初版设想的右侧。

```css
.message-navigator {
  position: absolute;
  top: 12px;
  bottom: 12px;
  left: 6px;               /* 贴近对话区左缘，落在 32px 左内边距内 */
  z-index: 8;
  display: flex;
  width: 20px;
  flex-direction: column;
  align-items: flex-start;
  justify-content: center;
  user-select: none;
  touch-action: none;
}
```

- 命中区宽度 `20px`，刻度左对齐并向右伸长：常态 `scaleX(0.5)`（视觉 8px），当前轮 `scaleX(1)`（16px），与参考图的"当前项更长"一致。
- 上下用 `top/bottom: 12px` 双向钉住，垂直居中交给 `justify-content`，避免 `top:50% + translateY(-50%)` 在高度变化时抖动。
- 轨道可见时 `.chat-feed` 左内边距加到 44px，防止刻度压住正文。
- 预览卡片从轨道**向右**展开（`left: 24px`），朝对话内容方向。

### 6.3 「回到底部」协同

现有 `.scroll-bottom` 位于 `right: 26px; bottom: 118px`，与轨道右侧位置冲突。调整为：

```css
.conversation-stage.has-navigator .scroll-bottom {
  right: 34px;   /* 让出轨道命中区 */
}
```

或在轨道可见时把按钮改为轨道底部的固定刻度（P2）。

### 6.4 轨道几何边界（可点击/可渲染范围）

轨道是绝对定位元素，必须用**显式的边界盒**约束，否则在空态、超长会话、窗口缩放、滚动到顶/底时会出现出屏、压字、与按钮重叠。

#### 6.4.1 纵向边界

| 边界 | 值 | 设定理由 |
| --- | --- | --- |
| 上边界 | `top: 12px`（相对 shell） | 避开 `.chat-header` 的 1px 分隔线视觉残留；与消息起始 padding 16px 呼应 |
| 下边界 | `bottom: 12px` | 避开 composer 上浮阴影（`.composer` 阴影扩散 ~10px） |
| 可用高度 | `H = shell 高 − 24` | 刻度分配的唯一输入，必须由**实测**得到，不写死 vh |
| 居中方式 | `top: 12px; bottom: 12px` + 内部 `justify-content: center` | **不用** `top:50% + translateY(-50%)`：后者在 H 变化时需要重算，且与 `max-height` 叠加易出现 1px 抖动 |

即把 §6.2 的写法改为：

```css
.message-navigator {
  position: absolute;
  top: 12px;
  right: 6px;
  bottom: 12px;              /* 上下同时钉住，高度由父容器决定 */
  z-index: 8;
  display: flex;
  flex-direction: column;
  align-items: flex-end;
  justify-content: center;   /* 刻度整体垂直居中 */
  gap: 5px;
  padding: 0 4px;
  user-select: none;
}
```

`H` 通过 `ResizeObserver` 观测 shell 得到（而非 `getBoundingClientRect` 每帧读），只在尺寸变化时重算 `unit`。

#### 6.4.2 轮次数量边界（决定"渲染几根刻度"）

| 轮次数 n | 行为 | 边界依据 |
| --- | --- | --- |
| 0–5 | 不渲染 | 短会话点两下滚动条即可，轨道是噪声 |
| 6–9 | 全量渲染，`gap: 8px` | 数量少，可放大间距提升可点性 |
| 10–60 | 全量渲染，`unit = clamp(2, (H − gap·(n−1)) / n, 8)` | `H=600` 时 60 轮仍能保持 5px 间距 |
| 61–90 | 全量渲染 + 轨道内部滚动 | `unit` 触底 2px 后不再压缩，改为滚动保鲜当前轮 |
| > 90 | 聚合模式，刻度数上限 60 | 见 §10.3；超过 90 根 2px 线人眼无法分辨，必须聚合 |

**硬上限**：刻度节点数永远 ≤ 60。这是渲染性能与可读性的共同边界，也是"性能要撑得住"的第一道闸门。

#### 6.4.3 横向边界

| 边界 | 值 | 说明 |
| --- | --- | --- |
| 轨道右缘 | 距 shell 右边缘 `6px` | 落在 `.chat-feed` 的 32px 右内边距内，不与内容区（max 760px 居中）交叠 |
| 命中区宽度 | `20px`（`padding: 0 4px` + 刻度列宽） | 视觉 8px，其余为透明命中区；小于 16px 时高频误触正文链接 |
| 卡片右缘 | 轨道左侧 `8px` | 卡片宽 300px，需满足 `shell 宽 − 760px − 32px ≥ 300px` |
| 卡片最小可用宽度条件 | shell 宽 ≥ 1152px | 不足时按 §10.5 隐藏轨道（而非压缩卡片，压缩会导致摘要只剩 1 行） |

#### 6.4.4 与内容的垂直安全距离

刻度不得与消息内容在同一纵向位置"贴脸"：内容区最大 760px 居中，在 1440px 窗口中左右各有 `(1440−280−760)/2 ≈ 200px` 空白，轨道天然落在空白内。但当窗口收窄到 1152–1280px 区间，空白降到 36–100px，此时：

- 刻度仍保留（与内容间距 ≥ 20px）；
- 卡片改为 `max-width: 260px` 并把摘要裁到 2 行；
- 窗口 < 1152px：轨道整体隐藏。

### 6.5 层级与让位边界

| 元素 | `z-index` | 与轨道的关系 |
| --- | --- | --- |
| 消息内容 / Markdown 链接 | 0 | 轨道在上，但轨道命中区不与内容交叠 |
| `.scroll-bottom`（回到底部） | 5 | 轨道可见时右移让位（§6.3） |
| `MessageNavigator` | 8 | — |
| 预览卡片 | 9（轨道内子元素） | 高于刻度，低于 Element UI 的 `el-dropdown`（1000+） |
| `el-dropdown` / `el-message` | ≥ 1000 | 始终在卡片之上，避免遮挡会话操作菜单 |

**让位规则（必须成对实现）**：

```css
/* 轨道可见时，会话舞台打标记 */
.conversation-stage.has-navigator .scroll-bottom { right: 34px; }
.conversation-stage.has-navigator .composer-wrap { /* 不变，避免误伤输入区 */ }
```

```js
// 页面计算属性，单一真值来源，避免模板里散落条件
hasNavigator() { return this.anchors.length >= NAV_MIN && this.navigatorVisible }
```

**禁止**让位与隐藏分别由两处条件控制（例如 CSS 按宽度隐藏、JS 按轮数隐藏），否则会出现"按钮已让位但轨道没显示"的空洞。所有显隐判断收敛到 `hasNavigator` 一个计算属性。

### 6.6 空态与极端几何

| 情形 | 轨道行为 |
| --- | --- |
| 会话为空 / 加载中 | 不渲染（`anchors.length === 0` 已自然覆盖） |
| shell 高度 < 200px（窗口被压扁） | 不渲染；此时刻度间距已无意义 |
| shell 高度 200–320px | 渲染但聚合到 ≤ 20 根刻度，卡片单行摘要 |
| 首次进入会话尚未测量到 H | 先不渲染，`ResizeObserver` 首帧回调后再显示（避免闪一下错位刻度） |
| 窗口拖拽缩放中 | 只在 `ResizeObserver` 回调里重算 `unit`，不做逐帧计算 |

### 7.1 刻度

| 属性 | 值 | 说明 |
| --- | --- | --- |
| 常规刻度 | `8 × 2px`，`border-radius: 1px`，`#d8dee9` | 轮次少时用 2px 线，密度高时视觉更稳 |
| hover 刻度 | `12 × 2px`，`#9aa7ba` | 横向伸长而非变粗，避免列宽抖动 |

## 8. 交互细节

### 8.1 悬浮预览

**落地修正（v0.4）：不能按"刻度 pointerenter"实现。** 刻度视觉高度只有 2px，鼠标几乎不可能精确落在某根线上，按逐刻度 `pointerenter` 会出现"必须点击才有反应"的体感。

实际实现分三点：

1. **整条轨道参与命中**：`pointermove` 绑在轨道根元素上，按纵坐标映射到最近刻度（`indexFromPoint`）。鼠标一进入轨道即开始 120ms 计时，不需要对准某根线。
2. **移动用 rAF 合并**：`pointermove` 只记录 `clientY` 并在同一帧内合并处理，避免高频事件反复创建/清除定时器造成跟手迟滞。卡片一旦显示，切换到相邻刻度**立即跟随**，不再等 120ms（只有"从无到有"才需要延迟，用于过滤快速划过）。
3. **滑向卡片不闪断**：卡片默认 `pointer-events: none`，若只靠刻度列命中，指针从刻度移向卡片时会穿过 4px 空隙落到正文上，轨道收到 `pointerleave`，160ms 后卡片消失。因此：
   - 悬停期间浮动卡片改为 `pointer-events: auto`（此时用户意图就是看卡片）；
   - 额外加一条 6px 宽、与卡片同高的**透明延伸带** `.message-navigator-hover-bridge`，覆盖"刻度列右缘 → 卡片左缘"的空隙；
   - 两者都是轨道的子元素，指针经过时不会触发 `pointerleave`。

其余规则：

- 离开该区域 160ms 后关闭卡片。
- 卡片内暂不放"跳转/复制"按钮，避免与正文链接争抢点击。
- 拖动中（§8.3）不显示卡片，改为在轨道顶部显示"第 n / N 轮"轻量标签，避免卡片跟随抖动。

### 8.2 点击跳转

```js
scrollToAnchor(anchor) {
  const feed = this.$refs.feed
  const el = feed && feed.querySelector(`[data-anchor-key="${anchor.key}"]`)
  if (!feed || !el) { this.scrollToRatio(anchor.index / this.anchors.length); return }

  const feedRect = feed.getBoundingClientRect()
  const elRect = el.getBoundingClientRect()
  const top = feed.scrollTop + (elRect.top - feedRect.top) - 12   // 12px 呼吸留白

  this.navigatorJumping = true      // 抑制自动跟随
  this.followScroll = false
  this.isUserScrolledUp = true
  feed.scrollTo({ top, behavior: prefersReducedMotion() ? 'auto' : 'smooth' })

  clearTimeout(this.navigatorJumpTimer)
  this.navigatorJumpTimer = setTimeout(() => { this.navigatorJumping = false }, 420)
  this.navigatorActiveKey = anchor.key
  this.flashAnchor(anchor.key)      // 1.2s 背景高亮淡出
}
```

关键点：

1. **不用 `scrollIntoView`**：它会把 composer 与 header 一起纳入可视区域计算，落点偏移不可控。
2. `navigatorJumping` 期间 `onFeedScroll` 不改写 `followScroll`（否则平滑滚动过程中会被 `distance > 80` 判成"用户上滑"，虽然结果一致但会让"回到底部"按钮出现/消失抖动）。
3. DOM 找不到时降级为比例定位 `scrollToRatio()`（为 §10.4 虚拟滚动预留）。

### 8.3 拖动 scrub（可选，v1 可关闭）

`pointerdown` 在轨道上进入 scrub 模式：`pointermove` 时按纵坐标映射到最近刻度，只更新 `hoverAnchorKey` 与"第 n / N 轮"标签；`pointerup` 才调用 `scrollToAnchor`。移动阈值小于 4px 时视为点击。用 `setPointerCapture` 保证移出轨道后仍能收到事件。

### 8.4 键盘

轨道容器 `tabindex="0"`，获得焦点后：

| 键 | 行为 |
| --- | --- |
| `ArrowUp` / `ArrowDown` | 在锚点间移动高亮（不立即滚动，仅显示卡片） |
| `Home` / `End` | 跳到第一轮 / 最后一轮 |
| `Enter` / `Space` | 跳转到当前高亮锚点 |
| `Escape` | 清除高亮并移出焦点 |

焦点环使用 `outline: 2px solid rgba(59,111,182,0.35); outline-offset: 2px`，与 Element UI 默认风格一致。

### 8.5 当前位置判定

不逐帧遍历 DOM。用 `IntersectionObserver`（`root: feed`，`rootMargin: '-12px 0px -60% 0px'`）观察全部 `[data-anchor-key]` 行，记录每条可见性；`activeKey` = 视口顶部 40% 区域内**最靠上**的可见锚点。观察器随 `messages.length` 变化重建（新消息到达时增量 observe，删除会话时 disconnect）。

无 `IntersectionObserver` 时回退到 `onFeedScroll` 内的 rAF 单次计算（取第一个 `rect.bottom > feedRect.top + 12` 的锚点）。

## 9. 与现有滚动逻辑协同

现有 `chatAutoScroll` 有三个状态：`followScroll`、`isUserScrolledUp`、`scroll()`。导航轨只新增两个状态：`navigatorActiveKey`、`navigatorJumping`，不改动原有语义。

| 场景 | 期望 | 实现 |
| --- | --- | --- |
| 流式输出中用户点击某轮 | 不被新内容拉回底部 | 跳转时 `followScroll = false`，并保持；`navigatorJumping` 阻止 scroll 事件回写 |
| 跳转后用户手动滚到底部 | 恢复跟随 | `onFeedScroll` 中 `distance <= 80` 时 `followScroll = true`，与现状一致 |
| 新消息到达且处于跟随态 | 轨道新增刻度，视口自动到底 | 派生 `anchors` 增加末项，`activeKey` 由观察器自然更新 |
| 切换会话 | 清空高亮与 hover | `loadSession` 时 `navigatorActiveKey = ''`、`hoverAnchorKey = ''`，并 disconnect 旧观察器 |
| 渲染模式切换（debug/elegant） | 锚点不变 | 锚点挂在 user 行，与助手渲染模式无关 |

`chatAutoScroll.js` 需要的最小改动：在 `onFeedScroll` 开头增加

```js
if (this.navigatorJumping) return
```

并为 `scrollToAnchor` 提供 `scrollToRatio(ratio)` 兜底方法（`feed.scrollTop = ratio * (feed.scrollHeight - feed.clientHeight)`）。

## 10. 边界与降级

### 10.1 短会话
- 轮次 `< 6`：不渲染轨道（`NAV_MIN = 6`）。
- 轮次 6–9：刻度间距放大到 8px，视觉上更易点。

### 10.2 超长会话（> 60 轮）
- 视觉密度改用 `unit` 计算（§7.1），最小 2px。
- 当 `unit` 触底时把轨道滚动起来（`overflow-y: auto`，`scrollbar-width: none`），保证当前轮刻度始终在轨道可视区内（`scrollIntoView({ block: 'nearest' })` 作用于轨道自身，`inline: 'nearest'`）。
- 卡片中补充"共 N 轮"提示，避免用户误以为漏轮。

### 10.3 聚合模式下（> 90 轮）
每 `ceil(n / 60)` 轮合并为一个"聚合刻度"，高度随合并轮数微增（2–6px）。hover 显示范围标题："第 61–63 轮"，摘要取组内首轮。点击跳到组内首轮。聚合只影响**视觉与预览**，滚动落点仍为真实锚点。该模式为 P1，可在首版先用"轨道滚动"方案顶住。

### 10.4 虚拟滚动（未来）
若后续引入消息虚拟列表，未挂载的锚点查不到 DOM：`scrollToAnchor` 走 `scrollToRatio()` 估算落点，滚动结束后重新校正一次（`requestAnimationFrame` 后二次对齐）。因为刻度是等距的，估算误差不影响使用体感。

### 10.5 其他降级
- 窗口宽度 `< 900px`：轨道隐藏（内容区仅 760px，右侧已无余量）。
- `prefers-reduced-motion: reduce`：跳转改为瞬时，取消脉冲与高亮淡出。
- 会话为空 / 加载中：不渲染。
- 会话历史异常（首条为助手消息）：`buildAnchors` 丢弃孤立助手消息，不产生空标题刻度。

## 11. 运行中场景同步（流式 / 等待 / 追加 / 中断）

这一节针对"会话正在运行"时必须同步的行为。现状代码里，流式每个事件都会深度修改 `answer` 对象并调用 `this.scroll()`（`ChatWorkbench.vue` `handleEvent` 末尾 `this.scroll()`），因此轨道如果直接依赖 `messages` 的深度变化派生锚点，**每个 token 都会重算一次**，这是性能与视觉稳定性的主要风险点。

### 11.1 运行中的四个状态阶段

| 阶段 | 代码特征 | 轨道应有的表现 |
| --- | --- | --- |
| 已提交、等首包 | `running = true`，`answer.status = 'running'`，`parts` 为空 | 立刻出现**新刻度**（不等到首包），状态为 `running`，脉冲 |
| 流式输出中 | `handleEvent` 持续 `appendResponseSegment` / `applyThink` / `applyTool` | 刻度量不变（轮次数不变），只更新该轮 `digest` 与 `toolCount`，**节流更新** |
| 等待用户确认 | `answer.status = 'waiting'`，`activeInterrupt` 非空 | 该轮状态切 `interrupt`（橙色），刻度加一个"待处理"标记 |
| 收口 | `resp_end` → `success`；`error` → `error`；`stop` → `cancelled` | 状态点定型，脉冲停止，摘要定格为最终内容 |

关键约束：**轮次数量在流式期间恒等于"已提交的用户消息数"**，`digest` 与状态才是变化量。因此不要用"整体重建 anchors"的方式更新，改为"尾项增量更新"。

### 11.2 增量更新：`diffAnchors`

新增纯函数，替代"每次全量 `buildAnchors`"：

```js
/**
 * 对比上一版锚点与当前 messages，返回最小更新指令。
 * 复杂度 O(changedTailPortion)，流式场景下通常只处理最后 1 个锚点。
 */
export function diffAnchors(prev, messages) {
  const next = buildAnchors(messages)
  if (next.length !== prev.length) return { replaced: next, tail: null }

  // 只有最后 k 个锚点的字段可能变化（流式只会改最后一轮）
  let from = next.length - 1
  while (from >= 0 && shallowEqual(next[from], prev[from])) from -= 1
  if (from < 0) return { replaced: null, tail: null }
  return { replaced: null, tail: { from, anchors: next.slice(from) } }
}
```

页面侧：

```js
// 节流包装，200ms 一次；running 为 false 时立即执行
scheduleAnchorSync() {
  if (!this.running) { this.commitAnchors(); return }
  if (this.anchorSyncTimer) return
  this.anchorSyncTimer = setTimeout(() => {
    this.anchorSyncTimer = null
    this.commitAnchors()
  }, 200)
}
```

- 只有 `tail` 时，用 `this.anchors.splice(from, 1, ...newTail)` 就地替换尾部，`MessageNavigator` 因为 `props.anchors` 引用变化仍会重渲染，但**刻度节点数不变**，Vue 2 的 `v-for` 加 `:key="anchor.key"` 会复用已有 DOM，不会整列重建。
- 派生成本：`buildAnchors` 是 O(n) 线性遍历，5000 条消息约 1–3ms；200ms 节流后对 60fps 渲染零影响。

### 11.3 运行中滚动与视口的关系

| 用户位置 | 新刻度到达时的视口 | 实现 |
| --- | --- | --- |
| 在底部（`followScroll === true`） | 自动跟随到底，`activeKey` 切到最新轮 | 现有 `scroll()` 保持不变；轨道 `activeKey` 由观察器更新 |
| 已上滑查看历史（`followScroll === false`） | **视口不动**，轨道在底部新增一根刻度并显示"新内容"小圆点 | 不做任何滚动干预；新增刻度不抢 `activeKey` |
| 处于跳转余韵窗口（`navigatorJumping === true`） | 视口保持目标轮，不被流式拉走 | `chatAnchorNav` 维持 `followScroll = false`，`onFeedScroll` 早退 |
| 用户确认了 interrupt（`waiting → running`） | 若原本在底部则继续跟随 | `submitInterrupt` 后调用 `resetScrollFollow()` 一次 |

"新内容小圆点"：`followScroll === false` 且 `anchors` 末尾 key 变化时，在轨道底部追加一个 `3px` 圆点（`#3b6fb6`），点击等同于"跳到最后并恢复跟随"。它替代现有 `.scroll-bottom` 在轨道可见时的部分职责，但**不删除**原按钮（保持兼容）。

### 11.4 流式期间的状态刷新优先级

同一轮可能同时命中多个状态，按固定优先级取一个（与 §5.1 一致，但在运行期需要动态覆盖）：

```text
interrupt（waiting） > error > running > cancelled > ok
```

注意运行期的特殊规则：

- `answer.status === 'waiting'` 时**必须**显示 interrupt 状态，即使该轮之前已有 `tool_card`。
- `stop()` 把状态置 `cancelled` 后，若该轮随后又收到 `resp`（理论上不会，但防御），保持 `cancelled`，不回到 `running`。
- `interrupt_resumed` 把状态从 `waiting` 回退到 `running` 时，脉冲恢复，但"待处理"标记立即移除。

### 11.5 运行中不做的三件事

| 不做 | 原因 |
| --- | --- |
| 流式期间自动滚动轨道到最新刻度 | 会让刻度在用户眼前持续跳动，破坏"空间位置稳定"的核心心智 |
| 每帧重算 `unit` / 轨道几何 | 几何只依赖 `H` 与 `n`，与内容长度无关 |
| 流式期间重建 `IntersectionObserver` | 锚点数量不变，只 observe 新增节点即可（§11.6） |

### 11.6 观察器的增量维护

```js
watch: {
  'anchors.length'(len) {
    if (len > this.observedCount) this.observeRange(this.observedCount, len)  // 只 observe 新增
    else if (len < this.observedCount) this.rebuildObserver()                 // 轮次减少（切会话/删除）才重建
    this.observedCount = len
  }
}
```

`loadSession` / `newChat` / `beforeDestroy` 三处必须 `disconnect()`，与 §4.5.1 提到的生命周期风险对应。

### 11.7 运行中与"停止/失败"的收口

| 动作 | 轨道变化 |
| --- | --- |
| 用户点"停止"（`stop()`） | 目标轮状态 `cancelled`，刻度变虚线；摘要保留最后一段文本的前 96 字 |
| 请求异常（`catch` 中置 `error`） | 刻度右侧红点，卡片显示错误标签 |
| 停止超时（`status 6` → `cancelled`） | 同停止 |
| 追加指令生效（`user_message` 事件） | 追加内容**不新增刻度**（属于同一轮的补充），仅在该轮卡片里显示"含 N 条追加指令" |

终态优先级规则（v0.4）：`cancelled` 是**终态**。用户点"停止"后，如果该轮仍残留一张状态为 `PENDING` 的中断卡片，不允许把状态重新提升为 `interrupt`，否则刻度会一直停留在橙色"待确认"并持续脉冲，与"已停止"的事实矛盾。实际产品路径上停止时会把残留卡置为 `CANCELLED`，此规则是防御性兜底。

最后一条很重要：`pendingAppends` 显示在 composer 上方，属"本轮补充"，若把它们也做成刻度，会造成"轮次数漂移"，与 §11.1 的核心约束冲突。

### 11.8 运行中的"末节点即当前位置"（v0.4）

运行中的会话有一个与静态会话不同的定位语义：**最后一个刻度就是"正在发生的位置"**，不需要等视口观测去推断。

原因：一轮回答可能比整屏还长。此时这一轮的用户消息早已滚出视口，`IntersectionObserver`（`rootMargin: -12px 0px -60% 0px`）在视口顶部 40% 区域内可能**一个锚点都命中不到**，结果是 `activeKey` 为空、整条轨道没有高亮——用户点进运行中的会话时会感觉"缩略导航没生效"。

因此运行期增加一条明确规则：

```js
// 视口顶部无任何命中，且会话在运行 → 当前轮直接取末节点
if (!active && running && anchors.length) activeKey = anchors[anchors.length - 1].key
```

并叠加"跟随态直接以末节点为准"：

```js
// 运行中且视口跟随底部时，当前轮恒为末节点，无需等待观察器回调
if (running && followScroll && lastKey) navigatorActiveKey = lastKey
```

两条规则合起来的语义正是用户期望的：

| 用户状态 | 轨道表现 |
| --- | --- |
| 点进一个正在运行的会话（默认在底部） | **末节点立即高亮并脉冲**，上面的刻度全部是历史轮次 |
| 运行中向上翻看历史 | 高亮跟随视口顶部命中的历史轮，末节点保留脉冲提示"仍在运行" |
| 翻回底部 | 高亮回到末节点 |
| 运行结束 | 高亮回到视口观测结果，脉冲停止 |

注意：末节点高亮**不代表**"把视口拉到底"。上滑查看历史时视口不能被动，这一点仍遵循 §11.3 与 §11.5（流式期间不自动滚动轨道）。

## 12. 性能设计

性能不是"预算表"，而是四道必须实现的机制。任何一道缺失，长会话都会退化。

### 12.1 机制一：派生层（纯函数 + 增量）

| 项 | 设计 |
| --- | --- |
| 派生位置 | `utils/messageAnchors.js` 纯函数，不依赖 Vue 响应式 |
| 调用时机 | `messages` 变化时，经 `scheduleAnchorSync()` 节流（运行中 200ms，空闲立即） |
| 增量策略 | `diffAnchors` 只返回尾部变更，页面 `splice` 替换 |
| 复杂度 | O(n) 单次遍历；流式下每次仅处理变更尾部 |
| 实测目标 | 5000 条消息全量 < 3ms；流式单次 < 0.2ms |

**禁止**：在 `computed` 里直接 `buildAnchors(this.messages)`。Vue 2 的 computed 依赖 `messages` 的深度变化，流式每个 token 都会触发重算 + 组件重渲染。

### 12.2 机制二：渲染层（刻度节点上限 + DOM 复用）

| 项 | 设计 |
| --- | --- |
| 刻度节点数 | 硬上限 60（§6.4.2），超出聚合 |
| `v-for` 策略 | `:key="anchor.key"`，key 稳定，避免整列重排 |
| 卡片 | **单实例**，切换刻度时只改 `transform: translateY()` 与文本，不 `v-for` |
| 状态点 | 用 CSS `::after` 而非额外 DOM 节点 |
| 动画属性 | 只动 `transform` / `opacity`，不动 `width`/`top`（避免 layout） |

刻度用 `transform: translateY()` 定位（`top` 由索引算出写进内联 style 一次），hover 时仅改 `transform: scaleX()` 与颜色，**不触发重排**。

### 12.3 机制三：观测层（不读布局）

| 项 | 设计 |
| --- | --- |
| 当前位置 | `IntersectionObserver`（`root: feed`），回调里只读 `entry.isIntersecting` 与 `boundingClientRect.top`（回调已提供，无强制 layout） |
| 几何测量 | `ResizeObserver` 观测 shell，只在尺寸变化时读一次 `clientHeight` |
| `onFeedScroll` | 只更新 `isUserScrolledUp` + 兜底 rAF 标记；**不查询 DOM** |
| 跳转计算 | 仅在点击时读 `getBoundingClientRect()`（低频，可接受） |

**禁止**：`onFeedScroll` 中 `querySelectorAll('[data-anchor-key]')` 后逐个 `getBoundingClientRect()`。30 轮以上每帧就是几十次强制同步布局，滚动会明显掉帧——这是本方案最容易犯的性能错误。

### 12.4 机制四：生命周期（防泄漏）

| 资源 | 创建 | 释放 |
| --- | --- | --- |
| `IntersectionObserver` | `mounted` 且 `hasNavigator` | `beforeDestroy` + 切会话时 `disconnect` |
| `ResizeObserver` | 同上 | 同上 |
| hover / 节流 / 跳转 `setTimeout` | 各交互点 | `beforeDestroy` 统一 `clearTimeout` |
| `pointermove` 监听（scrub） | `pointerdown` | `pointerup` / `pointercancel` 必须成对解绑 |

### 12.5 性能验收（可量化）

| 指标 | 门槛 | 测法 |
| --- | --- | --- |
| 100 轮会话打开 | 首屏 < 300ms，轨道出现 < 100ms | Performance 面板 |
| 流式输出期间 | 帧率 ≥ 55fps，无长任务 > 50ms | Performance 录制 30s |
| 滚动长会话 | 每帧脚本时间 < 4ms | Performance 面板 |
| 刻度节点数 | ≤ 60 | DOM 计数断言 |
| 切会话 20 次 | `IntersectionObserver` 实例数不增长 | `getEventListeners` / 手动计数 |
| 内存 | 30 分钟连续流式无持续增长 | Memory 快照对比 |

### 12.6 悬停热路径（v0.4 实测修正）

悬停是唯一"每秒可能触发上百次"的交互路径，最初实现里有两处会强制同步布局，实测表现为刻度跟手迟滞：

| 问题写法 | 后果 | 修正 |
| --- | --- | --- |
| `pointermove` 内 `list.getBoundingClientRect()` | 每帧强制布局，长会话悬停明显掉帧 | 缓存 `_geo`（`listTop` / `listOffset` / `rootHeight` / `step`），逐帧只做算术；仅在尺寸或聚合档位变化时刷新 |
| 每次切换刻度都 `root.querySelector('.mn-row.is-hover')` + `getBoundingClientRect()` | 每次悬停切换都查 DOM + 布局 | 按索引纯算术推导刻度中心（`listOffset + index*step + step/2`），卡片用 `transform: translate3d()` 跟手 |
| 每行都绑定内联 `:style="{ height }"` | 30–60 行 × 每次状态变化重建样式对象 | 行高与刻度高改用 CSS 变量（`--mn-row-h` / `--mn-tick-h`）在列表根节点下发一次 |
| 每次 `pointermove` 都 `clearTimeout` + `setTimeout` | 高频定时器抖动 | rAF 合并指针位置；卡片已显示时切刻度立即跟随，不再走 120ms 延迟 |
| 卡片高度每次都 `offsetHeight` | 每次切换都读布局 | 仅在切到**新锚点**时测量一次 |

验收口径：连续快速上下滑动轨道 30 次，`Performance` 面板中不应出现连续 >8ms 的强制布局块；卡片中心与悬停刻度中心偏差应 ≤1px（实测 0.1px）。

| Element UI 全局样式穿透 | 卡片字体/圆角被覆盖 | 卡片样式全部使用 `.message-navigator-*` 前缀，不用 `el-*` 类 |
| 摘要依赖 `message.content` | 工具轮次无正文，摘要为空 | 空摘要回退为"已运行 N 个工具 / 已读取文件"，见 §5.2 `toDigest` |
| 高 DPI 下 2px 线发虚 | 刻度看起来断裂 | 刻度用 `height: 2px` + 整数坐标；必要时 `transform: scaleY(0.5)` 的 1px 方案 |
| 流式期间全量重建锚点 | 每 token 触发重算与重渲染，滚动掉帧 | 强制走 `diffAnchors` + 200ms 节流，禁止 computed 直连 `messages` |
| 观察器随会话切换泄漏 | 长时间使用后内存增长、回调错乱 | `loadSession`/`newChat`/`beforeDestroy` 三处 `disconnect`，纳入验收 |
| 显隐条件分散 | 让位已生效但轨道未显示 | 统一收敛到 `hasNavigator` 计算属性 |
