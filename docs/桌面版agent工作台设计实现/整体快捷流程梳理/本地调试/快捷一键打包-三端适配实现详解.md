# 快捷一键打包（三端）适配实现详解

本文说明 AgentForge Desktop 如何用同一套 Vue + Electron + Java 代码生成三个桌面端安装包，以及打包脚本如何处理 CPU 架构、内置 JRE、后端 JAR、安装包格式和产物校验差异。

> 以当前仓库实现为准：本文的“三端”指 **macOS Apple Silicon (arm64)**、**macOS Intel (x64)** 和 **Windows x64**，不包含 Linux。

---

## 0. 先看结论

### 0.1 三个打包目标

| 目标标识 | 操作系统 | CPU 架构 | 打包命令 | 主要产物 |
| --- | --- | --- | --- | --- |
| `mac-arm64` | macOS | Apple Silicon arm64 | `npm run package:mac-arm64` | `.dmg` + `.zip` |
| `mac-x64` | macOS | Intel x64 | `npm run package:mac-x64` | `.dmg` + `.zip` |
| `win-x64` | Windows | x64 | `npm run package:win-x64` | NSIS `.exe` |

### 0.2 最快的本机打包方式

```bash
cd agentforge-desktop-ui
npm install
npm run doctor
npm run package:current
```

`package:current` 会根据 `process.platform + process.arch` 自动选择目标：

```text
darwin + arm64 -> mac-arm64
darwin + x64   -> mac-x64
win32 + x64    -> win-x64
其他组合        -> 直接报 Unsupported platform
```

### 0.3 “一键”的真实含义

当前实现的一键是：**一条命令完成当前目标的后端构建、运行时组装、前端构建、Electron 打包和产物校验**。

它不是在任意一台机器上一次生成全部三端：

- macOS arm64/x64 需要在 macOS 上打包；
- Windows x64 当前建议并实际要求在 Windows x64 上打包；
- macOS 到 Windows 的 `package:win-x64:cross` 入口已预留，但当前检查完 Wine/Docker 和 Windows JRE 后会明确 `process.exit(2)`，尚未真正开放跨端打包。

## 1. 整体快捷流程

```text
npm run package:current / package:<target>
  |
  |-- 1. 识别并校验目标平台
  |
  |-- 2. Maven 构建 Java 后端
  |      `-- agentforge-desktop-server.jar
  |
  |-- 3. 组装服务端运行时
  |      `-- runtime/server/agentforge-desktop-server.jar
  |
  |-- 4. 准备目标架构的 JRE 8
  |      `-- runtime/jre/
  |
  |-- 5. Vite 构建 Vue 渲染层
  |      `-- dist/
  |
  |-- 6. 校验 JAR 和 Java 可执行文件
  |
  |-- 7. electron-builder 按目标打包
  |      |-- mac-arm64/x64 -> .app + .dmg + .zip
  |      `-- win-x64       -> win-unpacked + NSIS .exe
  |
  `-- 8. 校验最终产物及内置 Java/JAR
```

统一编排入口是 `scripts/package/package-desktop.mjs`。它将多个独立脚本串成一个失败即停的流程，任意一步返回非 0 退出码，后续步骤都不会继续。

---

## 2. 命令入口如何做到统一

`package.json` 将人可读的 npm 命令映射为统一 target：

```text
package:current      -> package-current.mjs -> 自动检测 target
package:mac-arm64    -> package-desktop.mjs mac-arm64
package:mac-x64      -> package-desktop.mjs mac-x64
package:win-x64      -> package-desktop.mjs win-x64
package:mac -- --arch arm64|intel
                     -> package-mac.mjs -> 规范化为 mac-arm64/mac-x64
```

`package-mac.mjs` 还接受多种架构别名：

```text
arm64 / aarch64 / apple-silicon -> mac-arm64
intel / x64 / x86_64            -> mac-x64
```

这一层只负责“选目标”，真正的统一打包都会收敛到 `package-desktop.mjs`，避免三端各自维护一套重复流程。

---

## 3. 三端适配的核心：target 配置表

`package-desktop.mjs` 用一张 target 表描述差异：

| target | 允许的构建主机 | electron-builder 参数 | 产物命名 |
| --- | --- | --- | --- |
| `mac-arm64` | `darwin` | `--mac dmg zip --arm64` | `AgentForge Desktop-<version>-mac-apple-silicon-arm64.<ext>` |
| `mac-x64` | `darwin` | `--mac dmg zip --x64` | `AgentForge Desktop-<version>-mac-intel-x64.<ext>` |
| `win-x64` | `win32` | `--win nsis --x64` | `AgentForge Desktop-<version>-win-x64.exe` |

这种设计把“共性流程”与“平台差异参数”分开：

- 共性：构建 JAR、复制 JAR、复制 JRE、Vite build、electron-builder、产物验证；
- 差异：构建主机、CPU 架构、JRE 二进制、打包格式、文件名和校验规则。

---

## 4. Java 后端为什么可以共用

三端都内置同一个：

```text
runtime/server/agentforge-desktop-server.jar
```

构建流程是：

1. `build-server.mjs` 定位 Maven 和 JDK 8。
2. 检查 Maven 本地仓库中的 AgentForge 核心构件。
3. 核心构件缺失时，先对 AgentForge 核心模块执行 `mvn install`。
4. 对 `agentforge-desktop-server` 执行 `mvn clean package -DskipTests`。
5. `prepare-server.mjs` 把产物复制到 UI 项目的 `runtime/server`。

JAR 是跨平台 Java 字节码，所以三端不需要三份后端源码。真正与 OS/CPU 绑定的是运行 JAR 的 **JRE 二进制**，因此下一步必须为每个 target 单独准备 JRE。

---

## 5. 内置 JRE 是三端适配的关键

### 5.1 统一目录，不同二进制

无论哪个 target，打包前都把对应 JRE 放到：

```text
agentforge-desktop-ui/runtime/jre/
```

electron-builder 通过 `extraResources` 把它复制到安装包的 `resources/runtime/jre`。Electron 主进程只需使用统一相对路径：

```text
macOS/Unix -> resources/runtime/jre/bin/java
Windows    -> resources/runtime/jre/bin/java.exe
```

因此终端用户无需预先安装 Java，应用也不依赖系统 `JAVA_HOME`。

### 5.2 JRE 查找优先级

`prepare-jre.mjs` 依次查找：

```text
target 专用环境变量
-> packaging.config.local.json 的 jreHomes.<target>
-> AGENTFORGE_DESKTOP_JAVA_HOME
-> JAVA_HOME
-> macOS 常见 Zulu/Temurin 8 路径
```

target 专用环境变量：

| target | 环境变量 |
| --- | --- |
| `mac-arm64` | `AGENTFORGE_DESKTOP_JRE_HOME_MAC_ARM64` |
| `mac-x64` | `AGENTFORGE_DESKTOP_JRE_HOME_MAC_X64` |
| `win-x64` | `AGENTFORGE_DESKTOP_JRE_HOME_WIN_X64` |

找到候选项后会执行 Java 版本检查，必须是 Java 8。macOS 还会通过 `file <java>` 确认可执行文件是 `arm64` 还是 `x86_64`，防止把 Intel JRE 打进 Apple Silicon 包，或反之。

### 5.3 Windows JRE 的特殊处理

原生 Windows 打包走 `prepare-jre.mjs win-x64`，使用本地 Windows JRE 8。预留的 macOS -> Windows 跨端流程则走 `prepare-windows-jre.mjs`，来源优先级为：

```text
AGENTFORGE_DESKTOP_JRE_HOME_WIN_X64 / jreHomes.win-x64
-> AGENTFORGE_WINDOWS_JRE_ARCHIVE / jreArchives.win-x64
-> .cache/windows-jre/jre8-win-x64.zip
-> Adoptium API 下载 Windows x64 JRE 8
```

解压后会检查：

- `bin/java.exe` 和 `release` 是否存在；
- `release` 中的 `JAVA_VERSION` 是否为 `1.8`；
- `OS_ARCH` 是否为 `amd64/x86_64`。

## 6. 前端和 Electron 层如何保持跨端

### 6.1 Vue 前端

Vite 统一生成 `dist/`，这部分是 HTML/CSS/JavaScript，不区分 macOS 和 Windows。打包后 Electron 通过 `loadFile(.../dist/index.html)` 加载。

### 6.2 Electron 主进程

`electron/main.mjs` 中只对必要差异做平台分支：

- Windows Java 文件名是 `java.exe`，macOS 是 `java`；
- Windows 启动子进程使用 `windowsHide: true`，避免弹出命令行窗口；
- macOS 关闭最后一个窗口时保留 App，Windows 则退出；
- 开发者工具快捷键分别适配 `Command+Option+I` 和 `Ctrl+Shift+I`。

其余启动流程保持一致：选端口 -> 生成 Token -> `spawn(java, args)` -> 轮询健康检查 -> 注册 IPC -> 打开窗口。

### 6.3 打包资源布局

`package.json` 的 electron-builder 配置分两类文件：

```text
files:
  dist/**/*
  electron/**/*
  package.json

extraResources:
  runtime/server -> resources/runtime/server
  runtime/jre    -> resources/runtime/jre
```

Electron 应用本身进入 ASAR，Java/JAR 作为外部 resource 保持真实文件路径，便于直接启动可执行文件和 `java -jar`。

## 7. macOS 两端的适配细节

### 7.1 Apple Silicon arm64

```bash
export AGENTFORGE_DESKTOP_JRE_HOME_MAC_ARM64=/path/to/mac-arm64-jre8
npm run package:mac-arm64
```

关键限制：

- 必须在 macOS 上执行；
- JRE 必须是 Java 8 + Mach-O arm64；
- electron-builder 使用 `--arm64`；
- 解包目录默认为 `release/mac-arm64/`。

### 7.2 Intel x64

```bash
export AGENTFORGE_DESKTOP_JRE_HOME_MAC_X64=/path/to/mac-x64-jre8
npm run package:mac-x64
```

关键限制：

- 必须在 macOS 上执行；
- JRE 必须是 Java 8 + Mach-O x86_64；
- electron-builder 使用 `--x64`；
- 解包目录默认为 `release/mac/`。

### 7.3 macOS 后处理

`after-pack-mac.mjs` 只在 Darwin 产物上执行：

1. `xattr -cr <app>` 清理扩展属性；
2. `codesign --force --deep --sign - --timestamp=none <app>` 执行本地 ad-hoc 签名。

这可用于本地开发验证，但不等价于正式 Apple Developer ID 签名与 notarization（公证）。对外发布前还需要补齐证书、签名和公证流程。

---

## 8. Windows x64 适配细节

```powershell
$env:AGENTFORGE_DESKTOP_JRE_HOME_WIN_X64 = "C:\Tools\jre8-win-x64"
npm run package:win-x64
```

关键实现：

- electron-builder 使用 `--win nsis --x64`；
- NSIS 配置为 `oneClick: false`，使用安装向导；
- `allowToChangeInstallationDirectory: true`，允许用户选择安装目录；
- 安装包内必须是 Windows PE 格式的 `java.exe`，不能误打入 macOS Java；
- 当前未配置 Windows Authenticode 代码签名，对外发布前需补充证书配置。

### 8.1 为什么不建议直接从 macOS 生成 Windows 安装包

electron-builder 的 Windows/NSIS 跨端构建需要 Wine 或 Docker 环境，还要确保打入 Windows JRE。仓库已经实现：

- 检查 macOS 上的 Wine 或 Docker；
- 准备/下载 Windows x64 JRE 8；
- 校验 JRE 版本与架构。

但 `package-desktop.mjs` 紧接着会输出“Windows cross packaging is not enabled”并退出，因此 `npm run package:win-x64:cross` **现阶段不会产生 Windows 安装包**。稳定做法是在 Windows x64 主机或 Windows CI Runner 上执行原生打包。

## 9. 打包后自动校验了什么

### 9.1 macOS

`verify-mac-package.mjs` 检查：

- `.app` 是否存在；
- `<app>/Contents/Resources/runtime/jre/bin/java` 是否存在；
- `<app>/Contents/Resources/runtime/server/agentforge-desktop-server.jar` 是否存在；
- `release/` 下是否有 `.dmg`；
- 尝试执行 `codesign --verify --deep --strict`。

### 9.2 Windows

`verify-win-package.mjs` 检查：

- `release/win-unpacked` 是否存在；
- `resources/runtime/jre/bin/java.exe` 是否存在；
- `resources/runtime/server/agentforge-desktop-server.jar` 是否存在；
- `java.exe` 头两个字节是否为 `MZ` (`0x4D 0x5A`)，确认是 Windows PE 文件；
- `release/` 下是否存在 `win-x64*.exe` 安装包。

这些校验主要防止“安装包生成了，但内置后端无法启动”。它们属于结构校验，不替代在真实操作系统上的安装、启动和功能冒烟测试。

## 10. 本地配置示例

复制示例文件：

```bash
cd agentforge-desktop-ui
cp packaging.config.example.json packaging.config.local.json
```

根据本机实际路径修改：

```json
{
  "jreHomes": {
    "mac-arm64": "/Library/Java/JavaVirtualMachines/zulu-8.jdk/Contents/Home",
    "mac-x64": "/path/to/macos-x64-jre-8/Contents/Home",
    "win-x64": "C:\\Tools\\jre8-win-x64"
  },
  "jreArchives": {
    "win-x64": "/path/to/jre8-win-x64.zip"
  }
}
```

配置文件默认是 `agentforge-desktop-ui/packaging.config.local.json`。也可以用 `AGENTFORGE_PACKAGING_CONFIG` 指定另一个配置文件。

## 11. 建议的三端发布方式

如果目标是“一次发版自动得到三个终端产物”，最稳定的方案不是在一台开发机上强行交叉编译，而是 CI Matrix：

| CI Job | Runner | 命令 | 产物 |
| --- | --- | --- | --- |
| mac-arm64 | macOS arm64 | `npm run package:mac-arm64` | arm64 DMG/ZIP |
| mac-x64 | macOS x64 | `npm run package:mac-x64` | x64 DMG/ZIP |
| win-x64 | Windows x64 | `npm run package:win-x64` | NSIS EXE |

三个 Job 共用同一 commit 和版本号，完成后将 `release/` 产物上传到同一 Release。这才是用户视角真正的“一次触发、三端产物”。

当前仓库已经具备 target 拆分和各端命令，适合直接接入这种 CI Matrix；但本地脚本并没有名为 `package:all` 的三端并行编排入口。

## 12. 常见问题

### 12.1 `No JRE 8 found for <target>`

原因：没有找到对应 OS + CPU 架构的 Java 8。

处理：配置 target 专用环境变量，或在 `packaging.config.local.json` 中设置 `jreHomes`。

### 12.2 `JRE architecture mismatch`

原因：macOS arm64/x64 target 与实际 Java 二进制架构不同。

处理：用 `file <JRE_HOME>/bin/java` 检查，为两种 target 配置两套 JRE。

### 12.3 `should be packaged on darwin/win32`

原因：在错误的构建主机上执行了目标命令。

处理：macOS 包放到 macOS Runner，Windows 包放到 Windows x64 Runner。

### 12.4 `Embedded JRE/JAR missing`

原因：运行时准备失败，或 `runtime` 目录被手工清理。

处理：查看首个失败步骤，单独执行 `npm run build:server`、`npm run runtime:server` 和对应 `runtime:jre:*` 命令定位问题。

### 12.5 Windows 跨端打包为什么退出码是 2

这是当前代码主动设置的功能边界，不是本地环境偶发错误。请改用 Windows x64 原生打包。

## 14. 最终总结

三端支持不是通过复制三套应用代码实现的，而是通过以下分层完成：

1. **Vue 渲染层共用**：统一构建为 `dist/`。
2. **Java 服务端共用**：统一构建为可跨平台运行的 JAR。
3. **JRE 按 target 替换**：为 mac-arm64、mac-x64、win-x64 分别准备正确二进制。
4. **Electron 主进程小范围分支**：只处理文件名、窗口生命周期和快捷键等必要差异。
5. **electron-builder 按 target 出包**：macOS 产生 DMG/ZIP，Windows 产生 NSIS EXE。
6. **每端单独验证**：确保安装包内 Java 和 JAR 真正存在且格式正确。

所以，当前“三端一键打包”的技术本质是：**共用一条构建管线，通过 target 注入平台差异，在对应的原生构建环境中一条命令生成某一终端产物**。
