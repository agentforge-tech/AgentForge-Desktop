# 任务看板（右上角任务视角）

> 对应仓库：`AgentForge-Desktop`
> 涉及模块：`src/utils/taskBoardGroup.js`（新增）、`src/components/TaskBoardDialog.vue`（新增）、`src/pages/workbench/ChatWorkbench.vue`、`src/styles/chat.css`
> 版本：v1.0 · 2026-11-26
> 实现状态：**已实现，并用真实数据完成联调**

**一句话结论**：顶栏右上角加一个看板入口，点开居中弹窗，用「运行中 / 等待审批 / 已完成」三栏列出当前 Agent 的全部会话；绑定工作空间的会话打标识，每行「进入会话」直达并且**左栏自动展开选中**。**零后端改动**——`sessionList` / `topList` 返回的 `SessionVo` 已包含全部分类所需字段。

---

# 一、背景

## 1.1 问题

工作台一次只呈现一个会话。开多个任务后有三个痛点：

1. **不知道有几个在跑**：左栏虽有转圈图标，但混在「置顶任务 / 任务 / 工作空间」三组里，要逐组滚动扫描。
2. **不知道哪个在等我**：等待人工审批的会话停在原地，**没有任何汇总视图**，切走窗口后完全靠记忆。
3. **跑完的不知道去哪看**：完成提醒只有 Dock 跳动（见《任务完成提醒》），回来仍要自己找。

第 2 点是核心动因：**"在等我"比"在跑"更需要被看见**——它在阻塞推进，而"在跑"不需要用户做任何事。

## 1.2 目标

| 目标 | 说明 |
| --- | --- |
| 一个入口看全景 | 打开即见当前 Agent 的任务分布 |
| 三栏分类 | 运行中 / 等待审批 / 已完成，各自独立滚动 |
| 等待审批高识别 | 暖色强调 + 显示搁置时长 + 顶栏角标提示 |
| 工作空间可辨识 | 绑定的打标识，未绑定的显示弱化「默认空间」 |
| 一键进入会话 | 每行「进入会话」，**左栏同步展开并选中** |
| 零后端改动 | 不新增接口、不改表结构、不加 SSE |
| 不干扰当前会话 | 弹窗只读，打开不打断正在流的会话 |

## 1.3 非目标（v1 不做）

| 不做 | 原因 |
| --- | --- |
| 跨 Agent 聚合 | 接口按 `aid` 隔离，需新接口 → v2 |
| 实时进度 / 当前工具名 | 需按会话订阅 N 路 SSE，成本过高 |
| 看板内停止 / 删除 / **直接审批** | 审批必须在会话里看清上下文，弹窗点「同意」风险过高 |
| 已完成栏区分成功 / 失败 | 会话级状态分不出来（§2.2），→ v2 |
| 分页 / 搜索 | v1 取最近 50 条（§3.5） |

# 二、调研分析

## 2.1 状态字段：唯一可用的分类依据

`ai_agent_session.status`（`SessionStatusEnum.java:3-9`）：

```java
IDLE(0) / RUNNING(1) / FINISHED(2)
FAILED(3) / CANCELLING(4) / WAITING_HITL(5)
```

`SessionVo` 已带齐看板所需字段：`status`(:11)、`workspaceId`(:13)、`workspacePath`(:14)、`messageCount`(:20)、`lastMessageAt`(:21)、`running`(:19)。

**结论：不需要新接口。**

## 2.2 两个必须纠正的直觉

### ① `running` 不能用来分类

`AgentSessionService.java:265`：

```java
vo.setRunning(SessionStatusEnum.RUNNING.getCode().equals(session.getStatus()));
```

`running` **只在 `status==1` 时为 `true`**：

| 会话状态 | `status` | `running` | 用户感受 |
| --- | --- | --- | --- |
| 正在跑 | 1 | `true` | 运行中 |
| **等待审批** | 5 | **`false`** | 卡着等我点 |
| 取消中 | 4 | `false` | 正在收尾 |

若按 `running` 分栏，**等待审批的任务会掉进「已完成」**——用户最需要看到的任务被藏起来。

> 这不是推演：实测真实数据中 **3 条 `status=5` 全部 `running=false`**。

### ② 会话级状态分不出成功 / 失败 / 取消

`SessionLifecycleMiddleware.java:288-311` 的 `finishState()` **无条件**写 `FINISHED(2)`：

```java
agentSessionMapper.updateStatus(
        state.sessionPk, SessionStatusEnum.FINISHED.getCode(), finishedAt);
```

无论正常完成、异常失败（`:203`）还是用户取消（`:267`），**差异只落在 `ai_agent_session_message.status`，不落在会话上**。且 `FAILED(3)` 从未被写入会话表。

**取舍**：已完成栏徽标只用中性词（不用绿色对勾）；真实终态需读最新 AI 消息状态，属额外查询 → v2。

## 2.3 其他支撑事实

| 事实 | 依据 |
| --- | --- |
| **多任务并行是常态能力** | `chatTaskExecutor` core 2 / max 8 / queue 32（`ChatTaskConfiguration.java:13-24`） |
| 两个列表接口互补无交集 | `selectNormalList` 按 `pin_order=0`、`selectTopList` 按 `pin_order>0`，合并即全集 |
| 显式上限 50 | `MAX_LIMIT = 50`（`AgentSessionService.java`）；不传 `limit` 时返回全量 |
| 列表已含工作空间会话 | `workspaceGroups` 正是从 `[...topSessions, ...normalSessions]` 按 `workspaceId` 过滤 |
| 左栏 `isSessionRunning` 也不认 `status=5` | 只判 `running \|\| 当前会话在流`，故等待审批在左栏不转圈 |

## 2.4 后端接口契约（零改动复用）

看板**只调用两个已有接口**，都在 `AgentSessionController.java`，无新增、无修改。

### 通用约定

| 项 | 说明 |
| --- | --- |
| Base URL | 本地服务 `http://127.0.0.1:<port>`，端口每次启动随机（Electron 主进程注入） |
| 鉴权 | 请求头 `X-AgentForge-Desktop-Token: <token>`（`DesktopTokenFilter.java:20`） |
| 鉴权开关 | **服务端 token 为空时全放行**（`:37` `StringUtils.hasText(expected)`）；`OPTIONS` 预检直接放行 |
| 鉴权失败 | HTTP 401 + `{"code":401,"msg":"invalid desktop token"}` |
| 响应包装 | ⚠️ **这两个接口返回裸 `List`，不是 `ApiResponse` 包装**（controller 直接 `return List<SessionVo>`，项目无全局 `ResponseBodyAdvice`） |

> 前端 `api/client.js:39-42` 用 `if ('code' in body) return body.data` 判断：有 `code` 字段才解包。所以 `/api/local/health` 走解包分支，而会话列表接口直接拿到数组——两套响应形态并存，写代码时不能想当然。

### 接口一：`POST /api/agent/sessions/sessionList`

非置顶会话列表，按 `modify_time` 倒序。

```http
POST /api/agent/sessions/sessionList
Content-Type: application/json
X-AgentForge-Desktop-Token: <token>

{ "aid": "agt_default", "limit": 50 }
```

| 请求字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `aid` | String | **是** | 空则抛 `IllegalArgumentException("aid 不能为空")` |
| `limit` | Integer | 否 | `null` 或 `<=0` → 返回**全部**非置顶会话；显式传值则截断为 **50** 以内 |

```java
// AgentSessionService.java：limit 缺省即全量，显式传值才走窗口查询
if (limit == null || limit <= 0) {
    return toVoList(sessionMapper.selectAllNormalList(aid.trim()));
}
int size = Math.min(limit, MAX_LIMIT); // MAX_LIMIT = 50
```

底层 SQL（`AgentSessionMapper.java`）：

```sql
-- 全量（limit 缺省）：左栏与工作空间分组用它完整展示
SELECT * FROM ai_agent_session
WHERE is_deleted=0 AND aid=#{aid} AND pin_order=0
ORDER BY modify_time DESC

-- 窗口（显式 limit）：带 LIMIT #{limit}
SELECT * FROM ai_agent_session
WHERE is_deleted=0 AND aid=#{aid} AND pin_order=0
ORDER BY modify_time DESC LIMIT #{limit}
```

响应：`List<SessionVo>`（裸数组，见下方字段表）。

### 接口二：`POST /api/agent/sessions/topList`

置顶会话列表，按 `pin_order` 倒序，**无条数上限**。

```http
POST /api/agent/sessions/topList
Content-Type: application/json

{ "aid": "agt_default" }
```

| 请求字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `aid` | String | **是** | 同上校验 |
| `limit` | Integer | — | **复用同一 DTO 但服务层完全忽略**（`listTop` 不读它） |

底层 SQL（`AgentSessionMapper.java:48`）：

```sql
SELECT * FROM ai_agent_session
WHERE is_deleted=0 AND aid=#{aid} AND pin_order>0
ORDER BY pin_order DESC
```

### 两接口合并即全集

```sql
-- sessionList:  ... AND pin_order=0  LIMIT 50
-- topList:      ... AND pin_order>0  （无 LIMIT）
```

`pin_order` 只有"=0"和">0"两种取值，**两者互斥且完备**，合并后即当前 Agent 的全部可见会话。这是看板能做到"零后端改动"的根本原因。

### `SessionVo` 字段（看板实际用到 6 个）

| 字段 | 类型 | 看板用途 |
| --- | --- | --- |
| `id` | Long | 会话主键，`data-session-id` 定位、`enterFromBoard` 比对 |
| `status` | Integer | **三栏分类依据**（§3.1） |
| `workspaceId` | Long | 是否打工作空间标识；`null` = 默认空间 |
| `workspacePath` | String | 工作空间名兜底（名称查不到时取路径末段） |
| `messageCount` | int | 「N 轮」 |
| `lastMessageAt` | String | 相对时间 + 搁置时长（语义见 §4.4） |

> 其余字段（`sessionId`、`aid`、`title`、`modelId`、`context`、`topOrder`、`createTime`、`modifyTime`、`running`）也一并返回，但看板分类不依赖 `running`——原因见 §2.2。

### 前端调用位置

`src/api/session.js:5-11`（**无需改动**）：

```js
export function fetchSessionList(aid, limit) {
  return post(SESSION_BASE + '/sessionList', { aid, limit })
}
export function fetchTopSessionList(aid) {
  return post(SESSION_BASE + '/topList', { aid })
}
```

### 错误响应

参数校验失败由 `GlobalExceptionHandler` 兜底，返回 **HTTP 200 + 包装体**——注意与成功时的裸数组是两套形态：

```json
{"code": 400, "msg": "aid 不能为空"}
```

> 实测确认：HTTP 状态码仍是 **200**（不是 4xx），`data` 字段被全局 Jackson 配置省略——`application.yml:12` 设了 `default-property-inclusion: non_null`，`ApiResponse` 本身并无该注解。前端 `client.js` 的 `if (body.code !== 0) throw` 正好能捕获，不会把错误当数据。

### 接口行为实测（独立实例验证）

| 验证项 | 结果 |
| --- | --- |
| 无 token | HTTP **401** + `{"code":401,"msg":"invalid desktop token"}` |
| 带 token | 返回**裸数组**，首字符为 `[` |
| `aid` 为空 | HTTP 200 + `{"code":400,"msg":"aid 不能为空"}` |
| `limit` 缺省 | 返回 **全部**非置顶会话（不限条数） |
| `limit=999` | 截断为 **50** 条（`MAX_LIMIT`） |
| `topList` 传 `limit:1` | 仍返回全部置顶（服务层不读该参数） |

# 三、设计思路

## 3.1 分类口径（核心）

分类原则：**按"是否需要我"和"是否在推进"切分，而不是按"结束了没"。**

```
等待审批 = status == 5              → 阻塞中，等我操作
运行中   = status == 1              → 推进中，不需要我
已完成   = status ∈ {0, 2, 3, 4}    → 不需要我，且不再推进
```

三栏互斥且完备——`status` 只有 0–5 六个值，全部有归属：

| `status` | 归入栏目 | 栏内徽标 | 卡片附加信息 |
| --- | --- | --- | --- |
| 5 | **等待审批** | 无（栏名已表达） | 搁置时长 |
| 1 | **运行中** | 无（栏名已表达） | 转圈 + 相对时间 |
| 4 | **已完成** | 取消中 | 相对时间 |
| 2 | **已完成** | 已完成 | 相对时间 |
| 0 | **已完成** | 未开始 | 相对时间 |
| 3 | **已完成** | 失败（防御性保留） | 相对时间 |

### 为什么「取消中」放已完成

它是**瞬时态**：`ChatTaskServiceImpl.java:183` 先置 `CANCELLING(4)`，任务真停后由 `finishState()` 收口成 `FINISHED(2)`。

1. **语义一致**：用户点了取消 = 我不要再等，它不该继续占「运行中」吸引注意；
2. **不丢信息**：徽标显示「取消中」，不会被误认为已干净结束；
3. **无跳动感**：几秒后变「已完成」，卡片原地不动。

## 3.2 界面结构

**入口**：`.chat-toolbar` 内、`.mode-select` 之前（`mode-select` 受配置控制可能不渲染，入口不该依赖它）。

**弹窗**：`el-dialog`，`1080px` + `max-width: calc(100vw - 96px)`，`append-to-body`（避开 `.app-shell{overflow:hidden}`），`destroy-on-close`。

```
┌──────────────────────────────────────────────────────────────────┐
│ 任务看板                                    当前 Agent · 共 51 个 │
├──────────────────┬────────────────────┬──────────────────────────┤
│ 运行中  3        │ 等待审批  3  ⚠     │ 已完成  45               │
│ ──────────────── │ ────────────────── │ ──────────────────────── │
│ ◐ 重构看板视图   │ ⏳ 部署脚本确认    │ ✓ 修复登录态  [已完成]   │
│   📁 AgentForge  │   📁 ops-scripts   │   📁 AgentForge  2小时前 │
│   8分钟前·6轮    │   已搁置 1 天      │              [进入会话]  │
│        [进入会话]│          [进入会话]│ ✓ 调研通知    [未开始]   │
│                  │                    │   默认空间   昨天        │
│ 当前没有运行中的 │                    │ 仅显示最近 50 个任务     │
└──────────────────┴────────────────────┴──────────────────────────┘
```

**卡片三行**（320px 宽不溢出）：标题（单行省略 + `title` 全文）／工作空间标识／左侧时间+轮数 + 右侧「进入会话」。

**徽标只在已完成栏出现**：前两栏语义已由栏名表达，挂了就是重复噪声；已完成栏混合四种语义，必须逐条区分。

**响应式**：≥1000px 三栏并排（栏高 `min(56vh, 520px)`）；<1000px 纵向堆叠（每栏 `max-height: 28vh`）。

## 3.3 排序与角标

| 栏 | 排序 | 理由 |
| --- | --- | --- |
| 等待审批 | **搁置时长降序** | 越久没结论越可能被忽略，避免老任务被顶下去 |
| 运行中 / 已完成 | `lastMessageAt` 倒序 | 最近有动静的在上 |

置顶（`topOrder > 0`）**不参与**看板排序：它是左栏组织偏好，不是紧急度。

**角标**优先显示"等我"的数量（暖色），没有才显示"在跑"（灰色）：

```js
boardBadgeCount() {
  if (!this.backendConnected) return 0
  if (this.boardWaiting.length) return this.boardWaiting.length
  return this.boardRunning.length
}
```

## 3.4 职责切分

```
数据源 boardTopSessions / boardNormalSessions   ← 只存原始接口结果
   ↓
判定   groupSessions(list) → {running, waiting, done}   ← 纯函数，口径只此一处
   ↓
展示   TaskBoardDialog.vue                     ← props in / event out，无副作用
   ↓
副作用 ChatWorkbench.vue                        ← 取数 / 轮询 / 切会话 / 左栏联动
```

三个收益：**口径唯一**（角标、三栏、未来入口都调同一函数，不可能"看板说 3、角标说 2"）；**可验证**（纯函数可直接跑断言）；**可迁移**（组件无副作用，v2 做独立路由页可直接复用）。

## 3.5 边界

| 场景 | 处置 |
| --- | --- |
| 会话超 50 个 | 已完成栏底部固定「仅显示最近 50 个任务」 |
| 切换 Agent | **必须**清空列表 + 关弹窗。串台比空列表严重得多 |
| 后端未连接 | 图标 `disabled` + `title` 提示，不发请求不弹窗 |
| 工作空间已删除 | `clearWorkspace` 会置 `NULL`；名称仍有路径末段兜底 |
| 左栏与看板显示不一致 | 左栏不认 `status=5`，本版不改左栏 → §4.9 |

## 4.2 核心代码一：三栏分类

`src/utils/taskBoardGroup.js`：

```js
export const SESSION_STATUS = {
  IDLE: 0, RUNNING: 1, FINISHED: 2,
  FAILED: 3, CANCELLING: 4, WAITING_HITL: 5
}

const RUNNING_CODES = [SESSION_STATUS.RUNNING]
const WAITING_CODES = [SESSION_STATUS.WAITING_HITL]
const DONE_CODES = [
  SESSION_STATUS.IDLE, SESSION_STATUS.FINISHED,
  SESSION_STATUS.FAILED, SESSION_STATUS.CANCELLING
]

export function groupSessions(list) {
  const all = Array.isArray(list) ? list : []
  return {
    // 最近有动静的在上
    running: all.filter((i) => RUNNING_CODES.includes(Number(i.status))).sort(byActivityDesc),
    // 等待审批：越久没结论越靠前，避免老任务被新任务顶下去
    waiting: all.filter((i) => WAITING_CODES.includes(Number(i.status))).sort((a, b) => {
      return activityTime(a) - activityTime(b)
    }),
    // 最近完成的在上
    done: all.filter((i) => DONE_CODES.includes(Number(i.status))).sort(byActivityDesc)
  }
}
```

> `byActivityDesc` 即 `(a, b) => activityTime(b) - activityTime(a)`，抽出来避免两处重复。

三个易错细节：

| 细节 | 原因 |
| --- | --- |
| `Number(i.status)` | 接口若返回字符串 `"5"`，`=== 5` 会静默失配，任务凭空消失 |
| `Array.isArray(list) ? list : []` | 首次渲染列表是 `undefined`，不兜底会抛错 |
| 每栏各自 `sort` | `filter` 已产生新数组；共用中间数组会打乱入参顺序 |

## 4.3 核心代码二：角标常驻轮询（设计修正）

原方案"打开弹窗才拉数据 + 5s 轮询"，实测暴露硬伤：

```
点击图标前 角标 2  →  打开看板后 角标 3
```

角标的意义恰恰是"**在没打开时提示我**"，却依赖打开过看板。改为常驻轮询：

```js
scheduleBoardRefresh() {
  if (this.boardTimer) clearTimeout(this.boardTimer)
  if (this._isBeingDestroyed || this._isDestroyed) return
  // 打开时 5s（跟左栏节奏一致），关闭时降到 15s，兼顾实时性与空转成本
  const interval = this.boardOpen ? 5000 : 15000
  this.boardTimer = setTimeout(async () => {
    if (this.selectedAid && this.backendConnected && !this.boardLoading) {
      await this.refreshBoard({ silent: true })
    }
    if (this._isBeingDestroyed || this._isDestroyed) return
    this.scheduleBoardRefresh()
  }, interval)
}
```

配套两点：`closeBoard()` **不再 `clearTimeout`** 而是重新排程（自动切 15s 档）；`applyAgent()` 末尾补一次刷新，切换 Agent 后立即准确。

## 4.4 核心代码三：审批时长文案（设计修正）

```js
// 纯函数只算数
export function turnElapsedMinutes(item) {
  const at = activityTime(item)
  if (!at) return null
  return Math.max(0, Math.floor((Date.now() - at) / 60000))
}
```

```js
// 组件决定怎么说
waitingMeta(item) {
  const minutes = turnElapsedMinutes(item)
  if (minutes == null) return '等待你处理'
  if (minutes < 1) return '本轮刚进入等待'
  if (minutes < 60) return `本轮已进行 ${minutes} 分钟`
  const hours = Math.floor(minutes / 60)
  if (hours < 24) return `已搁置 ${hours} 小时`
  return `已搁置 ${Math.floor(hours / 24)} 天`
}
```

原方案只有「本轮已进行 N 分钟」，实测出现荒谬数字：

```
本轮已进行 2368 分钟     ← 约 1.6 天前挂在那的会话
```

改为分段后：`["已搁置 1 天", "已搁置 5 小时", "本轮已进行 12 分钟"]`。

> **为什么不写"已等待"**：`lastMessageAt = MAX(COALESCE(finished_at, create_time))`，审批态该轮消息尚无 `finished_at`，取到的是**本轮开始时间**，不是"进入审批时间"。超 1 小时改用「已搁置」正好绕开歧义——此时用户关心"这事儿凉了多久"。

## 4.5 核心代码四：进入会话 + 左栏联动

设计稿**遗漏**、落地补上的能力。原因很具体：`openSession()` 只设 `activeSessionId`，从不展开左栏分组；而工作空间会话条目包在 `v-show="expandedWorkspaceIds.includes(group.id)"` 里，**分组折叠时该条 DOM 根本不存在**。结果右侧打开了会话，左侧完全看不到它。

```js
enterFromBoard(item) {
  this.closeBoard()
  if (!item) return
  // 已在当前会话且正在流：不重复 openSession，避免无意义的 abort + 重连闪断
  if (item.id === this.activeSessionId && this.running) {
    this.revealSessionInSidebar(item)
    return
  }
  this.openSession(item)
},

revealSessionInSidebar(item) {
  if (!item) return
  // 工作空间会话：必须展开对应分组，否则条目根本不渲染
  if (item.workspaceId != null) {
    if (!this.workspaceOpen) this.workspaceOpen = true
    if (!this.expandedWorkspaceIds.includes(item.workspaceId)) {
      this.expandedWorkspaceIds.push(item.workspaceId)
    }
  } else {
    if (item.topOrder > 0) this.pinnedTasksOpen = true
    else this.normalTasksOpen = true
  }
  this.scrollSessionIntoView(item)
},

/** 等 DOM 更新（分组展开）后再滚动，否则元素还不存在。 */
scrollSessionIntoView(item) {
  this.$nextTick(() => {
    const container = this.$refs.sessionScroll
    if (!container) return
    const el = container.querySelector(`.session-item[data-session-id="${item.id}"]`)
    if (!el || typeof el.scrollIntoView !== 'function') return
    el.scrollIntoView({ block: 'nearest', behavior: 'smooth' })
  })
}
```

配套模板改动（否则选择器找不到元素）：

| 位置 | 改动 |
| --- | --- |
| 左栏滚动容器 | `ref="sessionScroll"`（`ChatWorkbench.vue:35`） |
| 三处会话条目 | `:data-session-id="item.id"`（`:42`、`:69`、`:161`） |

**关键设计**：`revealSessionInSidebar` 被调在 **`openSession` 内部**（`:952`），不只挂看板入口。这样从置顶任务、普通任务、未来任何入口打开会话，左栏都能保持一致。

## 4.6 实测结论

为不触碰正在使用的数据库，用**一致性备份 + 独立实例**验证（`sqlite3 .backup` 快照 → 独立端口启动）。

真实数据共 51 条可见会话：

| 栏目 | 数量 | 核对 |
| --- | --- | --- |
| 运行中 | 3 | status=1 共 3 条 |
| 等待审批 | 3 | status=5 共 3 条 |
| 已完成 | 45 | status=2 共 45 条 |
| **合计** | **51** | 与 `topList(1) + sessionList(50)` 一致 |

最关键的一条：

```text
status==5 且 running==false 的条数: 3
```

这 3 条正是等待审批的会话。若按最直觉的写法用 `running` 分类，它们会全部掉进「已完成」——用户最需要看到的任务被藏进已完成列表。**这条数据直接证明 §2.2 的结论不是理论推演。**

左栏联动实测：

```text
点击前：13 个工作空间分组，全部折叠（expandedCount = 0）
点击后：workspaceExpanded=true，activeInsideWorkspace=true
        activeTitle="任务看板方案设计"，headerTitle 同步
```
